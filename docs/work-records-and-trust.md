# NODE 데이터 원칙: 일의 기록 = 신뢰

이 문서는 `database/004_work_records_and_matching_data.sql`의 설계 기준입니다.
현재 단계는 사실·평가·선호·결과의 기록 기반입니다. AI 모델, 신뢰 점수, 추천 순위,
불이익 판정, 학습용 데이터 내보내기는 구현하지 않습니다. 운영 DB에도 적용하지 않았습니다.

## 서로 다른 세 축

| 축 | 질문 | 저장 근거 | 현재 처리 |
| --- | --- | --- | --- |
| 신뢰 | 약속과 실제 거래를 어떻게 이행했는가? | 확인된 활동·지급 기록, 출처·정정 이력 | 사실과 관측 범위만 제공, 점수/등급 없음 |
| 선호 | 본인이 어떤 일을 원하는가? | 작업자가 직접 선언한 직종·지역·단가·요일·기간의 버전 | 추측하지 않고 명시적 선호로 보관 |
| 작업 적합도 | 이번 일의 조건에 맞는가? | 당시 선호·채용 조건·일정·경력과 추천 문맥 | 입력 스냅샷/연결만 보관, 점수 없음 |

선호 불일치·채용 거절은 낮은 신뢰가 아닙니다. 높은 평점도 자격·일정 적합성을 대신하지 않습니다.
주관적 평가는 객관적 사실과 별도 테이블에 보관하고, 공통 종합 점수로 합치지 않습니다.

## 어떤 기록을 남기는가

| 요구 범위 | 구조 | 기록 원칙 |
| --- | --- | --- |
| 출퇴근·작업 완료 | `activity_records`의 check_in/check_out/work_completion | 일어난 시간과 기록한 시간을 분리, 작업일·매칭·보고자·당사자 구분 |
| 매칭·취소·재고용 | `match_events` → 활동/추천 결과 이력 | 확정/취소/완료 자동 기록, 같은 업체·작업자의 이전 완료 거래가 있을 때 재고용 연결 |
| 지급일·지연 입력 | payment_report/payment_receipt, 지급 의무·지급 신고 FK, 기록 시점의 지급기한 | 지급자 신고와 수령자 확인을 별도로 남김. 부분 금액도 보관 |
| 지급기한 변경 | `payment_due_date_history` | 지급 의무의 기한 변경 전후를 보존. 변경한 사용자를 모르면 추측하지 않음 |
| 작업 조건 변경 | 새 조건 버전으로 pending 매칭 생성 시 이전 terms와 연결 | 변경 사실과 양측 승인 여부를 구분. 변경했다는 이유로 감점하지 않음 |
| 상호 평가·재거래 의사 | `transaction_reviews` | 실제 확정 후 완료/취소된 거래의 당사자만 작성, 연락·약속 이행 평가와 재거래 의사 분리 |
| 직종·지역·단가·일정 선호 | `worker_preference_versions` + 직종·지역 연결 | 복수 직종/지역, 알 수 없는 값은 NULL, 실제 근무 가능 여부와는 별개 |
| 업체 채용 조건 | `hiring_condition_versions` + 날짜별 정원 | 직종·지역·단가·최소 경력·모집 형태·부분 일정·날짜/정원을 버전으로 보존 |
| 추천·조회·지원·선정·거절·결과 | `recommendation_impressions`, `recommendation_outcomes` | 양방향 노출 위치/정책 버전/시점/후속 결과. 유기적 유입은 impression FK 없이 보관 |

출퇴근·입금은 현재 수집 UI/API가 없으므로 이번 변경으로 실제 수집이 시작되는 것은 아닙니다.
이후 API는 활동 원장에 같은 트랜잭션으로 기록해야 합니다. 수집되지 않은 시간은 만들어 채우지 않습니다.
매칭/지원 상태는 기존 DB 경로에 기록 트리거를 연결했습니다. 과거 자료는 원래 `match_events`에
확정/취소/완료와 시간이 있는 경우만 정확히 옮깁니다. 과거 조회·출퇴근·수령·동의·재고용은 추정하지 않습니다.

기존 `applications`에는 선정/거절 담당자 필드가 없습니다. 상태 변경은 기록하되 담당자는 NULL로 둡니다.
후속 API에서 인증된 행위자를 전달하는 경로를 추가해야 합니다. 시스템이 행을 저장했다는 사실은
그 내용이 외부 증빙으로 검증됐다는 뜻이 아닙니다.

## 기록의 정확성

- `party_report`: 당사자 신고. 상대방 확인 전에는 `reported`이며 검증 사실로 승격하지 않습니다.
- `system_event`: 원본 DB 생애주기 이벤트 FK가 있는 기록. `system_recorded`는 시스템에 기록됐다는 뜻입니다.
- `server_snapshot`: 거래 조건 버전의 연결 기록. 새 조건 합의·계약 성립과는 다릅니다.
- `activity_confirmations`: 같은 거래의 독립된 상대방 확인. 자기 확인과 다른 거래의 확인을 거부합니다.
- `request_id`: 재시도 중복 방지 키. 호출자는 같은 요청의 재시도에 **같은 UUID**를 사용하고
  유일성 충돌 시 저장된 원본과 요청이 동일한지 비교해야 합니다. 기본 UUID는 비재시도 내부 기록용입니다.
- FK·당사자·작업일·금액 범위·지급 의무/신고 연결을 검사합니다. ID 인자는 인증을 대체하지 않습니다.
  서버는 세션에서 행위자를 결정해야 하며 클라이언트가 전달한 actor ID를 신뢰하면 안 됩니다.
- 지급 지연을 판단할 때는 약정 기한, 실제 지급/수령 주장 시각, 확인 상태, 부분 지급액, 시간대를 함께 봅니다.
  기한/수령일이 없으면 **미확인**입니다. 지연 0일이나 미지급 확정으로 바꾸지 않습니다.
  지급자 등록만으로 입금 완료가 되지 않으며 현재 DB는 지연 점수/확정 판정을 계산하지 않습니다.
- 같은 업체가 이전 완료 거래의 작업자를 다시 확정한 경우만 재고용으로 연결합니다.
  신규 조건에 대한 새 승인/확정은 기존 매칭 규칙을 그대로 따릅니다. 재고용이 없다는 것은 부정 신호가 아닙니다.

## 신규 가입자와 관측 범위

`trust_evidence_coverage`는 작업자/업체마다 관측 거래 수, 기록 수, 최초/최근 관측 시간을 제공합니다.
관측이 없으면 `history_status=no_history`, 있으면 `history_available`이고,
모두 `trust_assessment_state=not_assessed`입니다. 신뢰 점수·등급·낮음 기본값은 없습니다.
기록이 일부 있다는 것과 충분한 검증 표본이 있다는 것도 다릅니다.
향후 통계를 만들 때는 표본 수·관측 기간·출처별 확인 수준을 함께 표시해야 합니다.

신고·이의제기·취소·거절·미응답 자체로 감점하거나 신규 가입자를 배제하지 않습니다.
열린 분쟁/정정 대기/무효/대체된 원본은 검증 근거 집계에서 제외하지만, 그 제외를 불이익 신호로 사용하지 않습니다.
현재 집계는 기록 범위 안내일 뿐 순위나 선별 입력으로 연결되지 않습니다.

## 이의제기·정정·재심

1. 활동 또는 평가에 `record_cases`를 연결합니다. 당사자/원래 작성자가 사유 코드로 신청합니다.
2. 거래와 이해관계가 없는 관리자 계정이 `case_decisions`에 정책 버전과 결정을 남깁니다.
3. 정정 허용 후 새 원본 버전을 추가하고 `supersedes_id`와 해당 사건을 연결합니다.
   원본을 UPDATE/DELETE하지 않으며, 원본과 교체본은 함께 추적할 수 있습니다.
4. 상대방 확인이 필요한 교체된 활동은 다시 `reported`에서 시작합니다. 기존 확인을 복사하지 않습니다.
5. `effective_activity_records` / `effective_transaction_reviews`로 최신 유효 상태를 읽습니다.
   원시 테이블을 그대로 집계하거나 예전 학습용 자료를 그대로 재사용하면 안 됩니다.
6. 결정에 대한 재심은 같은 기록에 새 사건·결정을 남깁니다. 최신 결정을 반영하고 이전 결정은 보존합니다.

평가 공개는 아직 구현하지 않았습니다. 후속 UI는 상호 제출 전 비공개, 공개 시점, 보복 평가 방지,
열람 범위와 소명 절차를 결정해야 합니다. 주관적 평점·재거래 의사를 객관적 근무 사실처럼 표시하면 안 됩니다.

## 개인정보와 향후 학습

- 새 구조에는 이름·전화번호·생년월일·계좌·신분증·GPS·상세 주소·자유서술 평가를 복사하지 않습니다.
  기존 계정/업체/거래 ID와 필요한 시간·금액·시군구 수준 지역 코드만 연결합니다.
  ID도 재식별 가능한 개인정보입니다. 단순히 ID를 쓰는 것으로 익명화됐다고 간주하지 않습니다.
- 증빙 원본은 이 테이블/공개 저장소에 넣지 않습니다. 별도 접근 제어 저장소와 열람 로그가 준비된 뒤 연결합니다.
- 추천 기능용 기록과 학습 목적의 사용을 구분합니다. `learning_permission_events`는 개인과 업체의
  명시적 동의·철회·정책 버전을 따로 보관합니다. 개인은 본인, 업체는 소유자만 결정할 수 있습니다.
  `current_learning_permissions`에 행이 없으면 **동의 없음**입니다.
- 현재 학습 파이프라인/내보내기는 없습니다. 이후 도입 시 양측과 실제 개인정보 주체의 현재 동의,
  유효한 기록 상태, 목적/기간 제한을 확인하고 가명화해야 합니다. 업체 동의가 직원 개인의 동의를 대신하지 않습니다.
- 철회·정정·무효화 시 이미 만든 파생 자료에도 제외/재생성 처리가 필요합니다.
  학습 자료 버전/추출 시점/원본 ID 계보, 삭제 전파 절차를 갖추기 전에는 학습에 사용하지 않습니다.
- 추천 시점 이전의 `occurred_at`과 `recorded_at`만 특징으로 사용합니다.
  선택적 `feature_cutoff_at`은 shown_at보다 늦을 수 없고, 누락 시 당시 특징을 복원했다고 주장하지 않습니다.
  나중의 선정/거절/완료를 당시 입력으로 넣으면 미래 정보 누출이 됩니다.
- 미노출은 거절이 아니며 무조회/무응답은 싫어요가 아닙니다. 노출 위치·정책 버전을 함께 보관해
  노출 편향을 점검하고, 업체 거절을 작업자의 신뢰 라벨로 쓰지 않습니다.
- 새 원장/뷰에 PUBLIC 권한을 부여하지 않습니다. 서비스별 최소 권한과 당사자 열람 범위는 API 도입 시 설계합니다.

원장 불변은 일반 업무 경로의 원칙이지 무기한 보관의 근거가 아닙니다.
보관 기간과 법적 보존 범위는 운영 적용 전에 확정해야 합니다. privacy 사건의 무효 처리는 물리 삭제와 다릅니다.
정당한 삭제/가명화가 필요하면 제한된 개인정보 관리 절차에서 연계 원본·파생 자료·백업의 처리를 함께 검토해야 합니다.
일반 API에 임의 삭제 권한을 열거나 영구 미삭제를 약속하지 않습니다.

## 적용·검증 범위

새 DB는 001 → 002 → 003 → 004. 이미 003이 적용된 별도 DB는 004만 추가합니다.
001~003, 기존 계정/작업자/업체/매칭/지급 행과 ID를 변경하지 않습니다.
백업 및 별도 복제본에서 데이터 보존·기존 로그인·신규 원장 트리거를 검증한 뒤
운영 적용을 별도로 결정합니다. 서버 시작 시 자동 적용하지 않습니다.
004도 기록 트리거 설치·이전 중 원본 테이블의 쓰기를 잠그므로 유지보수 시간을 확보해야 합니다.

신뢰 점수·공개 평가 UI·출퇴근/입금 수집 API·전자서명·지급 판정·추천 모델·학습 내보내기·보존 기간 집행은
이번 데이터 기반과 구분되는 후속 작업입니다.
