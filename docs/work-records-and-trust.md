# NODE 데이터 원칙: 일의 기록 = 신뢰

이 문서는 `database/004_work_records_and_matching_data.sql`의 설계 기준입니다.

2026-10-27 운영정책 등록: [P-01~P-50](operating-policies.md)를 함께 따른다. 아래의 점수·공개·필터 미구현 표시는 현재 기반의 구현 범위이며, 신규 정책의 금지를 뜻하지 않는다. 초기 별점·주관적 평가 기능은 P-13에 따라 도입하지 않는다. 기존 평가 구조와 이력은 변경하지 않는다.

005의 [독립 검토 수정·운영 전 조건](pr-2-review-fixes.md)이 과거 귀속·결정 순서·시간 검증을 보강합니다.
현재 단계는 사실·평가·선호·결과의 기록 기반입니다. AI 모델, 신뢰 점수, 추천 순위,
불이익 판정, 학습용 데이터 내보내기는 구현하지 않습니다. 운영 DB에도 적용하지 않았습니다.

## 서로 다른 세 축

| 축 | 질문 | 저장 근거 | 현재 처리 |
| --- | --- | --- | --- |
| 신뢰 | 약속과 실제 거래를 어떻게 이행했는가? | 확인된 활동·지급 기록, 출처·정정 이력 | 사실과 관측 범위만 제공, 점수/등급 없음 |
| 선호 | 본인이 어떤 일을 원하는가? | 작업자가 직접 선언한 직종·지역·단가·요일·기간의 버전 | 추측하지 않고 명시적 선호로 보관 |
| 작업 적합도 | 이번 일의 조건에 맞는가? | 당시 선호·채용 조건·일정·경력과 추천 문맥 | 입력 스냅샷/연결만 보관, 점수 없음 |

선호 불일치·채용 거절은 낮은 신뢰가 아닙니다. 높은 평점도 자격·일정 적합성을 대신하지 않습니다.
주관적 평가는 객관적 사실과 별도 테이블에 보관하고, 공통 종합 점수로 합치지 않습니다.

## 어떤 기록을 남기는가

| 요구 범위 | 구조 | 기록 원칙 |
| --- | --- | --- |
| 출퇴근·작업 완료 | `activity_records`의 check_in/check_out/work_completion | 일어난 시간과 기록한 시간을 분리, 작업일·매칭·보고자·당사자 구분 |
| 매칭·취소·재고용 | `match_events` → 활동/추천 결과 이력 | 확정/취소/완료 자동 기록, 같은 업체·작업자의 이전 완료 거래가 있을 때 재고용 연결 |
| 지급일·지연 입력 | payment_report/payment_receipt, 지급 의무·지급 신고 FK, 기록 시점의 지급기한 | 지급자 신고와 수령자 확인을 별도로 남김. 부분 금액도 보관 |
| 지급기한 변경 | `payment_due_date_history` | 지급 의무의 기한 변경 전후를 보존. 변경한 사용자를 모르면 추측하지 않음 |
| 작업 조건 변경 | 새 조건 버전으로 pending 매칭 생성 시 이전 terms와 연결 | 변경 사실과 양측 승인 여부를 구분. 변경했다는 이유로 감점하지 않음 |
| 상호 평가·재거래 의사 | `transaction_reviews` | 실제 확정 후 완료/취소된 거래의 당사자만 작성, 연락·약속 이행 평가와 재거래 의사 분리 |
| 직종·지역·단가·일정 선호 | `worker_preference_versions` + 직종·지역 연결 | 복수 직종/지역, 알 수 없는 값은 NULL, 실제 근무 가능 여부와는 별개 |
| 업체 채용 조건 | `hiring_condition_versions` + 날짜별 정원 | 직종·지역·단가·최소 경력·모집 형태·부분 일정·날짜/정원을 버전으로 보존 |
| 추천·조회·지원·선정·거절·결과 | `recommendation_impressions`, `recommendation_outcomes` | 양방향 노출 위치/정책 버전/시점/후속 결과. 유기적 유입은 impression FK 없이 보관 |

출퇴근·입금은 현재 수집 UI/API가 없으므로 이번 변경으로 실제 수집이 시작되는 것은 아닙니다.
이후 API는 활동 원장에 같은 트랜잭션으로 기록해야 합니다. 수집되지 않은 시간은 만들어 채우지 않습니다.
매칭/지원 상태는 기존 DB 경로에 기록 트리거를 연결했습니다. 과거 자료는 원래 `match_events`에
확정/취소/완료와 시간이 있는 경우만 정확히 옮깁니다. 과거 조회·출퇴근·수령·동의·재고용은 추정하지 않습니다.

기존 `applications`에는 선정/거절 담당자 필드가 없습니다. 상태 변경은 기록하되 담당자는 NULL로 둡니다.
후속 API에서 인증된 행위자를 전달하는 경로를 추가해야 합니다. 시스템이 행을 저장했다는 사실은
그 내용이 외부 증빙으로 검증됐다는 뜻이 아닙니다.

## 기록의 정확성

- `party_report`: 당사자 신고. 상대방 확인 전에는 `reported`이며 검증 사실로 승격하지 않습니다.
- `system_event`: 원본 DB 생애주기 이벤트 FK가 있는 기록. `system_recorded`는 시스템에 기록됐다는 뜻입니다.
- `server_snapshot`: 거래 조건 버전의 연결 기록. 새 조건 합의·계약 성립과는 다릅니다.
- `activity_confirmations`: 같은 거래의 독립된 상대방 확인. 자기 확인과 다른 거래의 확인을 거부합니다.
- `request_id`: 재시도 중복 방지 키. 호출자는 같은 요청의 재시도에 **같은 UUID**를 사용하고
  유일성 충돌 시 저장된 원본과 요청이 동일한지 비교해야 합니다. 기본 UUID는 비재시도 내부 기록용입니다.
- FK·당사자·작업일·금액 범위·지급 의무/신고 연결을 검사합니다. ID 인자는 인증을 대체하지 않습니다.
  서버는 세션에서 행위자를 결정해야 하며 클라이언트가 전달한 actor ID를 신뢰하면 안 됩니다.
- 지급 지연을 판단할 때는 약정 기한, 실제 지급/수령 주장 시각, 확인 상태, 부분 지급액, 시간대를 함께 봅니다.
  기한/수령일이 없으면 **미확인**입니다. 지연 0일이나 미지급 확정으로 바꾸지 않습니다.
  지급자 등록만으로 입금 완료가 되지 않으며 현재 DB는 지연 점수/확정 판정을 계산하지 않습니다.
- 같은 업체가 이전 완료 거래의 작업자를 다시 확정한 경우만 재고용으로 연결합니다.
  신규 조건에 대한 새 승인/확정은 기존 매칭 규칙을 그대로 따릅니다. 재고용이 없다는 것은 부정 신호가 아닙니다.

## 신규 가입자와 관측 범위

`trust_evidence_coverage`는 작업자/업체마다 관측 거래 수, 기록 수, 최초/최근 관측 시간을 제공합니다.
관측이 없으면 `history_status=no_history`, 있으면 `history_available`이고,
모두 `trust_assessment_state=not_assessed`입니다. 신뢰 점수·등급·낮음 기본값은 없습니다.
기록이 일부 있다는 것과 충분한 검증 표본이 있다는 것도 다릅니다.
향후 통계를 만들 때는 표본 수·관측 기간·출처별 확인 수준을 함께 표시해야 합니다.

신고·이의제기·취소·거절·미응답 자체로 감점하거나 신규 가입자를 배제하지 않습니다.
열린 분쟁/정정 대기/무효/대체된 원본은 검증 근거 집계에서 제외하지만, 그 제외를 불이익 신호로 사용하지 않습니다. 이는 P-22의 분쟁 등록·해결에 따른 분쟁 통계 갱신을 제외한다는 뜻이 아니며, 분쟁 발생 사실과 확정 귀책을 구분합니다.
현재 집계는 기록 범위 안내일 뿐 순위나 선별 입력으로 연결되지 않습니다. 후속 P-19 필터는 이용자의 명시적 선택으로 제공하며 기본 검색 자동 배제와 구분합니다.

## 이의제기·정정·재심

다음 1~6은 기존 DB 기반의 사건·원본 버전 관리 구조를 설명한다. 확정 근무 기록의 업무상 정정은 P-32에 따라 거래 상대방에게 요청하고 승인 시 정정한다. 거부 시 기존 기록을 유지하며 이의 제기로 관리하고 일괄 정정을 지원한다. 시스템 자체 오류만 운영자가 확인 후 정정할 수 있다. 기존 관리자 사건 결정을 모든 근무 정정의 운영자 승인 요건으로 해석하지 않는다. 정정 전후·처리 이력과 P-23의 통계 재계산 원칙을 유지하며 해당 업무 흐름 구현은 후속 작업이다.

1. 활동 또는 평가에 `record_cases`를 연결합니다. 당사자/원래 작성자가 사유 코드로 신청합니다.
2. 거래와 이해관계가 없는 관리자 계정이 `case_decisions`에 정책 버전과 결정을 남깁니다.
3. 정정 허용 후 새 원본 버전을 추가하고 `supersedes_id`와 해당 사건을 연결합니다.
   원본을 UPDATE/DELETE하지 않으며, 원본과 교체본은 함께 추적할 수 있습니다.
4. 상대방 확인이 필요한 교체된 활동은 다시 `reported`에서 시작합니다. 기존 확인을 복사하지 않습니다.
5. `effective_activity_records` / `effective_transaction_reviews`로 최신 유효 상태를 읽습니다.
   원시 테이블을 그대로 집계하거나 예전 학습용 자료를 그대로 재사용하면 안 됩니다.
6. 결정에 대한 재심은 같은 기록에 새 사건·결정을 남깁니다. 최신 실체적 결정을 반영하고 이전 결정은 보존합니다. 재심 기각은 앞선 실체적 결정을 유지합니다.

평가 공개는 아직 구현하지 않았습니다. 후속 UI는 상호 제출 전 비공개, 공개 시점, 보복 평가 방지,
열람 범위와 소명 절차를 결정해야 합니다. 주관적 평점·재거래 의사를 객관적 근무 사실처럼 표시하면 안 됩니다.

## 개인정보와 향후 학습

- 새 구조에는 이름·전화번호·생년월일·계좌·신분증·GPS·상세 주소·자유서술 평가를 복사하지 않습니다.
  기존 계정/업체/거래 ID와 필요한 시간·금액·시군구 수준 지역 코드만 연결합니다.
  ID도 재식별 가능한 개인정보입니다. 단순히 ID를 쓰는 것으로 익명화됐다고 간주하지 않습니다.
- 증빙 원본은 이 테이블/공개 저장소에 넣지 않습니다. 별도 접근 제어 저장소와 열람 로그가 준비된 뒤 연결합니다.
- 추천 기능용 기록과 학습 목적의 사용을 구분합니다. `learning_permission_events`는 개인과 업체의
  명시적 동의·철회·정책 버전을 따로 보관합니다. 개인은 본인, 업체는 소유자만 결정할 수 있습니다.
  `current_learning_permissions`에 행이 없으면 **동의 없음**입니다.
- 현재 학습 파이프라인/내보내기는 없습니다. 이후 도입 시 양측과 실제 개인정보 주체의 현재 동의,
  유효한 기록 상태, 목적/기간 제한을 확인하고 가명화해야 합니다. 업체 동의가 직원 개인의 동의를 대신하지 않습니다.
- 철회·정정·무효화 시 이미 만든 파생 자료에도 제외/재생성 처리가 필요합니다.
  학습 자료 버전/추출 시점/원본 ID 계보, 삭제 전파 절차를 갖추기 전에는 학습에 사용하지 않습니다.
- 추천 시점 이전의 `occurred_at`과 `recorded_at`만 특징으로 사용합니다.
  선택적 `feature_cutoff_at`은 shown_at보다 늦을 수 없고, 누락 시 당시 특징을 복원했다고 주장하지 않습니다.
  나중의 선정/거절/완료를 당시 입력으로 넣으면 미래 정보 누출이 됩니다.
- 미노출은 거절이 아니며 무조회/무응답은 싫어요가 아닙니다. 노출 위치·정책 버전을 함께 보관해
  노출 편향을 점검하고, 업체 거절을 작업자의 신뢰 라벨로 쓰지 않습니다.
- 새 원장/뷰에 PUBLIC 권한을 부여하지 않습니다. 서비스별 최소 권한과 당사자 열람 범위는 API 도입 시 설계합니다.

원장 불변은 일반 업무 경로의 원칙이지 무기한 보관의 근거가 아닙니다.
보관 기간과 법적 보존 범위는 운영 적용 전에 확정해야 합니다. privacy 사건의 무효 처리는 물리 삭제와 다릅니다.
정당한 삭제/가명화가 필요하면 제한된 개인정보 관리 절차에서 연계 원본·파생 자료·백업의 처리를 함께 검토해야 합니다.
일반 API에 임의 삭제 권한을 열거나 영구 미삭제를 약속하지 않습니다.

## 적용·검증 범위

새 DB는 001 → 002 → 003 → 004 → 005. 기존 DB는 미적용 버전만 추가하며 005의 검토 대응표가 필요할 수 있습니다.
001~003, 기존 계정/작업자/업체/매칭/지급 행과 ID를 변경하지 않습니다.
백업 및 별도 복제본에서 데이터 보존·기존 로그인·신규 원장 트리거를 검증한 뒤
운영 적용을 별도로 결정합니다. 서버 시작 시 자동 적용하지 않습니다.
004도 기록 트리거 설치·이전 중 원본 테이블의 쓰기를 잠그므로 유지보수 시간을 확보해야 합니다.

신뢰 점수·공개 평가 UI·출퇴근/입금 수집 API·전자서명·지급 판정·추천 모델·학습 내보내기·보존 기간 집행은
이번 데이터 기반과 구분되는 후속 작업입니다.


## 신규 운영정책과의 경계

- P-08: 관리자는 기록 정정·허위정보 확인·보안 관리를 수행할 수 있으나 거래 분쟁을 직접 중재하거나 귀책을 판정하지 않는다. 기존 사건 결정은 플랫폼 기록의 유효성 관리 범위와 구분해 해석한다.
- P-09~12: 분쟁 발생과 귀책을 분리한다. 취소율의 분모는 전체 확정 매칭 건수이며, 귀책 인정 근거·이견 처리 상세는 미확정이다.
- P-15·16: 지원 전/선정 전 통계를 제공하되 분쟁 상대방 신원·주장 상세·개인정보는 공개하지 않는다. 거래 상세는 당사자, 관리자 접근은 별도 권한에 따른다. 근무 기록의 구체적 열람 범위는 P-36, 작업자 직접 제출은 P-38을 따르며 상세 권한 구현은 후속 검토한다.
- P-17·19: 전체 누적과 최근 12개월 통계 및 이용자 선택 필터를 제공하는 정책이다. 아직 구현되지 않았다.
- P-07: 매칭 확정 당시 지급 약속과 실제 지급·수령 확인을 구분한다. 수령 미확인을 미지급·귀책으로 자동 확정하지 않는다. NODE는 대금을 보관·송금하지 않는다.
- P-20·21: 매칭 이력이 없으면 「거래 기록 없음」, 완료율·취소율·분쟁률은 「산정 불가」로 표시한다. 첫 매칭부터 누적하고 건수·비율을 함께 표시한다. 1건부터 실제 통계를 제공하고 확정 매칭 5건 미만은 「기록 적음」을 안내한다. 신규·소표본에 따른 기회 제한이나 통계 숨김은 금지한다.
- P-22·23: 취소 확정·양측 완료·지급/수령 확인 완료·분쟁 등록/해결에 따라 자동 갱신하고 지연 시 마지막 갱신 시각을 표시한다. 오류 확인 후 정정하고 전후 내용·사유·시각을 보존하며 재계산한다. 불리하다는 이유만으로 삭제하지 않는다.
- P-24~26: 계약 단위 통계와 실제 근무일수를 분리한다. 중도 종료의 실제 근무 이력과 계약 전체 완료 여부를 각각 보존한다. 작업자 귀책/업체 귀책/상호 합의/불가항력/분쟁 중을 구분하고 확정 귀책만 취소 통계에 반영한다. 날짜별 양측 확인과 이견 처리는 다른 날짜에 영향을 주지 않는다.
- P-27·28: 근무 완료만 기본 확인하며 출퇴근·실제 작업시간은 구분해 선택 입력한다. 일치한 작업시간만 확정하고 여러 날짜를 일괄 처리할 수 있다. GPS 위치 추적·위치 기반 인증은 제외한다.
- P-29·30: 상대방 확인 요청·이의 제기·재알림을 지원한다. 미응답 자동 승인 없이 확인 대기로 유지한다. 작업자 본인 및 해당 현장 권한이 있는 업체 담당자의 확인과 확인·변경자/시각 이력을 보존한다. 담당자 변경에도 기존 기록·확인 이력을 유지한다.
- 근무 확인의 24시간 재알림·72시간 장기 확인 대기는 P-31, 담당자 지정·회수는 P-33으로 확정한다. 재알림 반복·통합 구현, 대금 수령 미응답 상세, 세부 현장 권한 운영 절차는 후속 검토한다.

## P-31~P-40과 기록·열람·제출의 경계

- P-29·31: 최초 요청 후 24시간 재알림, 72시간 미응답 시 장기 확인 대기. 자동 승인·미응답 불이익 없이 언제든 확인/이의 제기가 가능하며 장기 대기 건수는 본인에게만 표시하고 공개 신뢰 통계에서 제외한다.
- P-23·32: 확정 근무 기록의 당사자 정정은 상대방 승인 절차를 따른다. 거부 시 기존 기록을 유지하고 이의 제기로 관리하며 전후 내용·처리 이력을 보존한다. 시스템 자체 오류는 운영자 확인 후 정정할 수 있다. NODE의 거래 분쟁 귀책 판정 금지는 유지한다.
- P-30·33: 현장별 복수 확인 담당자, 퇴사·권한 상실 시 회수, 신규 담당자의 미확인 기록 처리를 지원하고 기존 처리자 이력을 유지한다.
- P-28·34·35: 업체는 여러 작업자, 작업자는 자신의 여러 날짜를 일괄 확인한다. 사전 대상·날짜·건수 표시, 분쟁/이의 기록 제외, 개별 확인자·시각 보존을 따른다. 동일 현장 요청은 통합하고 분쟁/이의 알림은 구분하며 작업자에게도 같은 통합 원칙을 적용한다.
- P-16·36·38: 개별 기록의 기본 비공개와 확정 범위의 통계 공개를 유지한다. 작업자 본인 전체 열람, 업체의 현장별 열람 권한, 정당한 운영자 접근과 접근 이력을 구분한다. P-38은 작업자가 선택하여 직접 제출한 범위에 한해 수신 업체가 열람하는 경로이며 원본 수정이나 미제출 상세 기록 공개를 허용하지 않는다.
- P-37~40: 선택한 본인 이력을 상태 구분·발급일과 함께 PDF/엑셀로 출력하고 다른 작업자 개인정보를 제외한다. 제출 범위·수신 업체·시각을 기록하고 고유 확인번호 또는 QR로 발급·위변조 및 NODE 기록과의 일치 여부를 확인한다. 이는 법적 증명·실제 근무의 법적 보증이 아니다. 정정 시 기존 발급 문서의 변경 사실을 표시하며, 철회 즉시 NODE 내 열람을 중단한다. 이미 외부에 보관된 문서의 회수 불가를 사전 안내하고 원본 삭제·법령상 보존과 구분한다.

다운로드·제3자 제출은 학습용 데이터 내보내기와 구분한다. P-37~40은 정책 등록이며 수집 API·출력·진위 확인·철회 기능이 구현됐음을 뜻하지 않는다. 출력·제출·접근 이력의 보존 및 법령상 자료 처리의 세부 기준은 후속 검토한다.

## P-41~P-50: 원본 근무 기록과 제출 문서의 구분

원본 근무 기록의 정정·확인·통계 산정은 P-22~26·32를 유지한다. 제출 문서는 발급 당시 이력을 담은 고정 문서이며 발급번호·기간·접근 권한·제출 및 열람 이력을 원본과 구분해 관리한다. 이 문서의 기존 개인정보를 원장에 복사하지 않는 DB 기반 설명은 P-43의 동의 기반 선택 공개를 금지하는 뜻이 아니며, 공개 저장소나 기존 원장에 개인정보를 추가 저장하라는 지시도 아니다.

- P-38·40·41·50: 제출 시 7일/30일/90일을 선택하고 만료 시 열람을 자동 종료한다. 만료 전 조기 철회가 가능하다. 유효한 문서의 연장은 수신 업체 요청과 작업자 승인·새 기간 선택을 따르며 미승인 시 기존 만료일을 유지한다. 만료·철회 문서는 연장하지 않고 새로 제출한다. 원본·제출 이력 보존과 다운로드 사본 회수 불가 원칙을 유지한다.
- P-36·38·42: 수신 업체에서도 권한 있는 채용·인력관리 담당자만 제출 문서를 열람한다. 일반 직원은 제외하며 퇴사·권한 상실 시 즉시 종료하고 열람자·시각을 기록한다. 문서 유효기간과 철회 제한을 함께 적용한다.
- P-43·46·50: 이름·연락처·거주 지역은 각각 선택 공개하고 근무 이력 핵심 정보는 유지한다. 제출 전 실제 표시 내용을 미리 확인하며 미승인 정보는 공개하지 않는다. 확대는 별도 동의가 필요하고 재제출 시 다시 선택한다. 연장은 내용·공개 범위를 변경하지 않는다.
- P-44·49: 제출 내역의 열람 가능/기간 만료/권한 철회 관리와 미열람/열람 완료/기간 만료/권한 철회 상태 표시를 연결한다. 수신 업체·제출일·공개 정보·유효기간·현재 상태와 업체별 열람 기록을 본인이 확인한다. 최초 열람 시각은 반복 열람에도 유지하고 철회 후 제출 이력도 보존한다. 상태가 겹칠 때의 표시 우선순위와 내부 상태 구조는 미확정으로 남긴다.
- P-45·48: 제출·열람 알림과 동일 업체의 제출 알림 통합을 적용한다. 제출 알림에는 제출자·유효기간을 표시한다. 만료 24시간 전 업체 담당자와 작업자에게 알리되 이미 열람했거나 철회된 문서는 제외한다. 만료 시 권한 종료 자체는 유지한다.
- P-39·46·47: 근무 기록 원본과 발급 당시 고정된 제출 문서를 구분한다. 추가 근무 기록은 재제출로만 제공하며 별도 발급번호·권한을 부여하고 기존 문서를 자동 삭제·변경하지 않는다. 원본 정정 시 변경 사실을 표시하되 기존 문서 본문을 자동 변경하지 않는다. P-47의 기존 기간·권한 유지는 내용 추가·정정에 의한 자동 변경 금지이며 P-40·41·42·50의 철회·만료·권한 종료·승인 연장과 함께 적용한다.
- P-39·40: 진위 확인은 NODE 기록과 문서의 일치 여부 확인이며 실제 근무의 법적 보증이 아니다. 철회 즉시 NODE 내 열람을 중단하고 다운로드 사본은 회수할 수 없다. 철회·만료 후 진위 확인의 노출 범위와 정정 표시 전달 방식은 후속 검토한다.

미열람·기간 만료·철회·연장 요청/승인/거절 등 제출·열람 행위를 이유로 신뢰 통계의 불이익을 부과하지 않는다. 열람 완료는 채용 의사나 근무 사실 인정이 아니며 기존 객관적 거래 지표를 대체하지 않는다. 원본 정정에 따른 통계 재계산과 고정된 제출 본문·정정 사실 표시는 구분한다. 기록 보존은 기존 법령상 삭제·보존 원칙과 함께 적용하며 무기한 보존으로 해석하지 않는다.

### 후속 검토 — 구현·운영 세부사항 미확정

- 연장 승인 시 새 기간의 기산점·만료 시각 계산 및 시간대 처리.
- 미열람/열람 완료와 기간 만료/권한 철회가 겹칠 때의 표시 우선순위·내부 상태 구조.

## 2026-10-28 B 정책 연결 및 충돌 5건 정정 (정책 확정, 구현 승인 아님)

- P-15·16 / B7-17: 업체 선정 전 신뢰 통계를 제공하며 자동매칭 추천 작업자의 계약 완료율도 계약 확정 전에 확인할 수 있다. 개인별 상세 근무 기록·분쟁 내용은 이 공개에서 제외한다. 상세 기록의 별도 열람·본인 제출은 P-36·38을 따른다. 무이력만으로 자동매칭에서 제외하지 않는다.

- P-05 / B4: 작업자 귀책 확정 시 매칭권 1회 차감, 잔액 부족은 현금 채무 없는 차감 대기로 처리한다. 업체에는 대체 작업자 또는 다음 구인 건 수수료 1회 면제를 제공하며 매칭권을 대체 작업자에게 직접 지급하지 않는다. 긴급 공고 상위 노출은 유지한다. B4의 선부담·이월·정정 원칙도 유지한다.
