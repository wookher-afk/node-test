# 업체 내부 구인공고 등록·조회 — 첫 개발 단위

기준: `b5d6ac6a5e56a7e3464d00765db6bd44f618455e`와 이번 사용자 개발 지시. 기존 정책 230건·마이그레이션 001~006은 변경하지 않는다. 이번 범위의 owner/manager 제한은 임시 개발 접근 범위이며, 담당자 위임을 영구 금지하는 정책이 아니다.

## 지급 기준과 미결 경계

사용자가 이번 작업 중 다음을 확인했다. **당일·익일 지급은 여러 작업일 각각을 기준으로 한다.** 당일은 해당 근무일, 익일은 그 다음 달력 날짜, 날짜 지정은 공고에 명시한 날짜다. 전체 작업 종료일 기준 지급과 분할 지급은 이번 범위에 없다. 관련 근거는 P-01·P-07·B6이며 실제 법정 지급기일 판단이나 합의로 법정 의무를 면제하는 기능은 아니다.

비활성 현장에 새 공고를 등록할지에 대한 답은 확인되지 않았다. 그 부분은 구현 완료나 영구 금지 정책으로 확정하지 않고, 현재 API는 신규 등록을 409로 보류한다. 비활성 현장의 기존 공고 조회·기록은 유지한다. 현장 비활성화가 공고를 자동 종료하거나 기존 거래를 변경하지 않는다.

## API

기존 Bearer 세션을 사용한다. 본문 수신·JSON 및 기본 형식 검증을 DB 연결/공통 잠금 전에 완료한다. 기존 `(710031,1)` 잠금 획득 뒤 실제 시각 기준 세션 만료, 현재 소속·owner/manager 역할, 현장 범위를 다시 검사한다. 현재 staff의 현장 edit/confirm_work 권한은 이번 공고 권한으로 해석하지 않는다. 작업자 또는 타 업체에게 열람을 허용하지 않는다.

| 메서드·경로 | 입력·출력 |
| --- | --- |
| POST `/api/worksites/:siteId/job-posts` | 아래 입력. 201 `{job_post: {...}}` |
| GET `/api/worksites/:siteId/job-posts` | 해당 현장 공고와 모집 항목·날짜 전체. 200 `{job_posts: [...]}` |
| GET `/api/job-posts/:postId` | 현장 소속까지 재검증한 단건. 200 `{job_post: {...}}` |

```json
{
  "visibility": "public",
  "lines": [
    {
      "occupation_id": "3",
      "resource_mode": "worker",
      "allow_partial": true,
      "pay": {"unit": "day", "amount_krw": 250000},
      "payment": {"mode": "next_day"},
      "dates": [
        {"work_date": "2030-11-01", "capacity": 2},
        {"work_date": "2030-11-02", "capacity": 3}
      ]
    }
  ]
}
```

- visibility를 생략하면 기존 DB 기본값인 public. public/targeted/private를 보존하지만 외부 노출·지정 대상 관리 API는 없다.
- lines 및 각 dates는 하나 이상이며 같은 항목 안에서 작업일은 중복할 수 없다. 하나의 현장에 복수 공고, 하나의 공고에 복수 직종·조건 항목을 등록할 수 있다.
- occupation_id와 경로 ID는 양의 bigint 문자열. 실제 존재하는 직종인지 잠금 뒤에 확인한다.
- resource_mode는 기존 worker/equipment_and_worker/equipment 값을 보존한다. 장비 등록이나 매칭 지원이 완료됐다는 의미는 아니다. allow_partial은 필수 불리언이다.
- pay는 필수이며 unit은 이번에는 day만 허용한다. 금액은 JSON 안전 정수이며 기존 DB의 0 이상 범위를 유지한다. 0을 협의 금액으로 해석하지 않는다. 월급·시간급을 일당으로 변환하거나 기존 값을 삭제하지 않는다.
- payment는 필수. mode는 same_day/next_day/date. date일 때 due_date가 필수이고 당일·익일에는 due_date를 직접 입력하지 않는다. YYYY-MM-DD를 검증하고 익일은 월말·윤년·연말을 포함한 날짜 덧셈으로 계산한다. JSON 날짜를 브라우저 지역 시간으로 변환하지 않는다.
- 정원은 1~2147483647의 정수. 확정 인원은 confirmed/completed 매칭의 실제 참여 날짜로 계산하고 pending/cancelled는 제외한다. 잔여 인원은 정원에서 그 수를 뺀다. 지원자 수·선정 수를 확정 수로 사용하지 않는다.
- 반환 날짜별 항목은 work_date, capacity, confirmed_count, remaining_count, payment_due_date. 급여 금액과 bigint ID는 반환 시 문자열로 정밀도를 보존한다.
- 공고의 version, promise_version_id, 생성자·생성 시각, 현장 당시 기본정보와 모집 항목을 반환한다. 지원자 신원·연락처·승인자·계약 본문·실제 지급 상세는 반환하지 않는다. payment는 지급 약속이며 실제 지급 기록이 아니다.
- 입력에 업체/현장/행위자/역할/버전 위조 필드나 지원하지 않는 필드를 넣으면 거부한다. 버전은 서버가 1부터 부여한다.

오류는 기존 `{error: "설명"}` 형식이다. 400은 입력/직종 오류 또는 범위 밖 지급 방식, 401은 인증 실패, 403은 같은 업체의 역할 부족, 404는 없는 대상/타 업체다. 409는 미결인 비활성 현장의 등록 또는 현장 이관 후 과거 공고 스냅샷의 업체 귀속 검토가 필요한 상태다. 이관된 과거 스냅샷을 새 업체에 자동 공개하지 않는다.

## 007 마이그레이션과 보존

`database/007_internal_job_posts.sql`은 006 이후 한 번 적용하는 트랜잭션 마이그레이션이다. 기존 현장·공고·항목·날짜 ID와 외래키는 유지한다.

- job_posts에 version(기본 1), created_by/updated_by/updated_at(기존 행 NULL)을 추가한다. 기존 created_at은 그대로 보존한다.
- job_post_versions는 공고·업체·현장 귀속, 당시 현장 기본정보, 공개 범위, 기록자·시각을 보존한다.
- job_post_version_lines는 모집 항목별 직종·자원 유형·부분 허용·급여 단위/금액·지급 조건을, job_post_version_dates는 작업일·정원·그 날짜의 약정 지급일을 보존한다. 금액은 근무자 1명의 해당 근무일 일당이며 모집 정원 전체의 예산이 아니다.
- 작성 중 자식 행을 추가한 뒤 한 번 봉인한다. DB는 현재 모집 항목·날짜·정원이 빠짐없이 일치하는지와 지급일 계산을 검증한다. 미봉인 버전은 COMMIT할 수 없고 봉인 후 조건·지급 약속을 변경/삭제하거나 날짜를 추가할 수 없다.
- job_post_events는 신규 작성·기존 DB 변경·버전 봉인 이력을 추가 기록한다. 고정 search_path의 좁은 SECURITY DEFINER 트리거만 원장에 쓰며 런타임 직접 쓰기와 PUBLIC 함수 실행은 허용하지 않는다.
- 과거 지급 약속·작성자·현장 스냅샷·조건 버전을 현재 값에서 추정 생성하지 않는다. 버전 기록이 없는 기존 공고는 promise_version_id/worksite_snapshot/payment/payment_due_date를 NULL로 반환한다. 기존 일당·직종·정원 등 실제로 있는 필드는 그대로 조회한다.
- 등록은 기본 공고·모집 항목·날짜·지급 약속·버전·이력을 한 트랜잭션에 저장한다. 실제 payment_obligations·매칭·지원·예약은 생성하지 않는다.

공고 version과 match_terms의 협의 버전은 별개다. 이번에는 기존 지원·협의·계약을 재연결하거나 바꾸지 않는다. 향후 수정 API는 새 공고 버전과 재동의 업무를 함께 설계해야 하며 현재 DB의 과거 매칭 당사자 스냅샷도 유지해야 한다.

## 실행·검증 및 남은 범위

공고 DB 역할은 회원·현장 역할과 별도인 로컬 임시 역할이다. `JOB_POST_DATABASE_URL`은 회원 DB와 같은 호스트·포트·DB·옵션이어야 한다. 회원 정보 변경, 현장 수정, 공고 수정/마감, 지원·승인, 계약·실제 지급 상세, 원장 직접 쓰기 권한이 없다. 정원 집계에 필요한 매칭 ID/상태/항목/날짜 컬럼만 읽는다. 서버의 업체 격리를 사용자별 RLS 완성으로 표현하지 않는다. DB 자격은 신뢰된 서버에만 둔다.

`npm run dev:local`은 준비된 로컬 DB에 세 임시 역할을 구성하고 정상 종료 시 제거한다. 기존 안전장치가 있는 `npm test`만 독립 node_test DB를 초기화하며 001~007 신규 설치, 기존 데이터 업그레이드, 007 마지막 단계 실패 롤백, 기존 회귀와 신규 HTTP/동시성 테스트를 실행한다. 서버 시작과 Docker 시작은 마이그레이션을 실행하지 않는다. 운영 DB/역할/비밀 설정은 별도 승인과 복제본 리허설 대상이다.

이번에는 공고 수정·마감·작업자 검색/열람·지원·선정·매칭·알림·실제 지급·비활성 현장의 기존 공고 종료·지원 상태 변경·UI를 구현하지 않는다. 공고 목록은 현재 현장 전체 목록이며 대규모 목록의 페이지 처리는 후속이다. 지원 마감 시각·자동 모집 종료·공개 대상 전달·필수 자격 검증은 후속 범위로, 이번 내부 등록의 open 상태를 외부 모집·지원 가능 보장으로 해석하지 않는다. 기록 보존기간·법적 지급기일 검증·실제 계약별 지급 의무 산출도 임의 확정하지 않는다.
