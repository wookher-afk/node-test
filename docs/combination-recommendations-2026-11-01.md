# NODE 3단계 복수 작업자 일정 조합 추천

작업 브랜치: `feature/node-alpha-01-worker`. 기존 미커밋 변경을 유지하며 별도 GET 경로를 추가했다. UI, DB 스키마, 기존 정확 매칭 및 개별 추천 판정·정렬은 변경하지 않았다. 수락·예약·가격확정·커밋·푸시·배포·병합은 수행하지 않았다.

## API 및 해석

`GET /api/companies/:organizationId/combination-recommendations`

기존 인증과 업체 멤버십 조회를 사용한다. 하나의 읽기 스냅샷에서 업체 버전과 작업자 버전을 반환한다. `readOnly`, `policy`, `limits`, `status`, `results`를 포함한다. 연락처·원본 등록정보는 반환하지 않는다.

모집항목별 하나의 결정적 제안이다. 가능한 모든 대안의 열거 기능은 제공하지 않는다. `assignments`에 작업자 ID·등록 버전, `proposedPeriods`(양 끝 포함), 배정일수, `price`(업체 제시액, 작업자 희망액, 부호 있는 차이, 절대 차이, 부족액, 급여 단위)를 제공한다. 일급이면 원/일이며 다른 단위를 일급으로 환산하지 않는다. `requestedPeriods`, `requestedDays`, `headcount`, `requiredWorkerDays`, `coveredWorkerDays`, `uncoveredWorkerDays`, `fullyStaffedDays`, `complete`, `dailyCoverage`, `gaps`로 기간과 인원 부족을 함께 표시한다. `gaps`는 날짜별 부족 인원이다. `fullPeriodIndividualIds`는 기존 개인 추천 순서다.

업체와 배정된 각 작업자 모두 수락해야 확정된다는 문구를 정책 데이터에 명시했다. 반환 금액은 희망 조건이며 확정 거래가격이 아니다. 실제 수락·가격확정 기능은 없다.

## 조합 방법과 보장

기존 `recommendWorkers`를 재사용하여 정확 장비 규격, 옵션·경력·기본 조건과 업체가 선택한 필수조건을 모두 통과한 후보만 배정한다. 업체 일정 필수 선택 시 부분 일정 작업자는 제외한다. 기존 개별 추천의 기간 충족도 → 절대 가격 차이 → ID 순서는 그대로다.

각 요청 날짜에서 가능한 서로 다른 작업자를 최대 `headcount`명 배정한다. 동일 작업자가 같은 날짜의 두 모집 자리를 채울 수 없다. 동일 ID의 중복 입력은 버전 충돌 여부를 추정하지 않고 모두 제외하며 해당 ID를 표시한다. 같은 작업자가 떨어진 날짜 구간에 재등장하는 것은 가능하다.

이 모델에서는 날짜 간 추가 제약이 없으므로 날짜별 `min(필요 인원, 가능한 고유 작업자 수)`의 합이 충족 인일의 정확한 상한이고, 구현은 그 상한을 달성한다. 하루 필요 인원을 모두 채운 날짜 수도 최대화한다. `optimalCoverage: true`는 이 모집항목의 입력 후보 집합에 대해서만 성립한다.

전체 기간 가능한 단독 작업자를 우선한다(복수 모집이면 해당 작업자로 먼저 자리를 채움). 이후 기존 배정 작업자를 유지하고, 연속 가능 잔여 기간이 긴 작업자를 선택하며, 동점은 기존 개인 추천 순서를 따른다. 인원·교대 수의 전역 최소해는 보장하지 않는다. 이 후순위는 `secondaryOptimization: heuristic-provisional`, `temporaryTieBreaks: true`로 명시했으며 가중합 점수를 영구 정책으로 확정하지 않았다.

## 예시

업체 2026-11-02~30, 1명, 550,000원/일:

| 작업자 | 가능 기간 | 제안 기간 | 희망 일급 | 업체 대비 차이 |
|---|---|---|---:|---:|
| A | 11/02~17 | 11/02~17 | 550,000원 | 0원 |
| B | 11/14~30 | 11/18~30 | 570,000원 | +20,000원 |

29/29일 충족, 공백 0일. 두 명 모집이면 58인일 중 33인일 충족, 부족 25인일, 11/14~17만 두 명 모두 충족한다. 다른 전체 기간 가능 작업자가 있으면 그 작업자의 단독 추천이 우선된다.

## 폭증 방지 및 제한

후보 1,000명, 항목 50개, 요청 날짜 366일, 모집인원 50명 이내이며 요청 전체의 날짜×고유 후보 연산 예산은 2,000,000이다. 조합 열거를 하지 않고 날짜별 정렬로 처리한다. SQL도 조합 경로에서 작업자 1,001개까지만 읽어 한도 초과를 감지한다. 초과 시 후보를 조용히 자르지 않고 `input_limit`, `schedule_limit`, `unsupported_headcount`, `computation_limit` 등을 반환한다. 비명시·잘못된 일정은 `unspecified_schedule`/`invalid_schedule`로 표시한다. 한도 초과 항목에는 최적 조합을 주장하지 않는다. 기존 두 경로는 이 한도를 적용하지 않는다.

## 미확정 정책 질문

- 동일 충족량에서 총 투입 인원, 실제 교대, 희망 가격 차이 중 무엇을 먼저 최소화할지, 허용 인원·교대 상한은 얼마인지?
- 최소 연속 배정일·재등장 허용·공휴일·휴무·이동시간·기존 예약 충돌을 어떻게 적용할지?
- 여러 모집항목은 독립 대안이다(`independentAlternative`). 항목 간 같은 사람의 동시 배정을 조정하는 전역 추천은 별도 정책·개발이 필요하다.
- 여러 대안을 몇 개 표시할지? 현재 한 개 제안이다. 많은 후보·장기 모집의 제품 한도와 페이지 조회 정책은 별도 확정이 필요하다.
- 인원 부족일에 일부 인원이라도 배정하는 현 모델과, 특정 날짜를 우선하는 현장 정책 중 무엇을 사용할지?

## 검증 및 보존

최종 실행 결과와 보존 확인은 같은 이름의 자료 폴더 `combination-2026-11-01/`에 기록한다. 단위 테스트는 실제 달력 경계·윤일·불연속·겹침·공백·인원수·중복 ID·필수조건·단독 우선·입력 비변경·결정성·입력 한도와 최대 지원 규모를 검증한다. 생성된 30개 소규모 일정에서 날짜별 완전탐색 상한과 인일 충족량도 비교한다.

격리 검증 스크립트는 매번 새 `node_test_combination_<timestamp>` DB만 생성·초기화하고 제한된 런타임 역할로 HTTP 테스트를 실행한다. 종료 시 새 DB·역할을 제거하고 기존 DB 목록·ACL 및 역할 속성·설정의 전후 일치를 검증한다. 기존 DB 전체 데이터 덤프 비교는 하지 않았다.

최초 통합 실행에서 새 테스트의 임시 작업자가 기존 개별 추천 테스트 순위 묶음에 끼어든 테스트 격리 문제를 발견했다. 새 테스트가 만든 등록만 정리하도록 수정했다. 기존 개별 추천 테스트와 엔진은 수정하지 않았다.
