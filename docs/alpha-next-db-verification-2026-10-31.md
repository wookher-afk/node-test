# NODE Alpha 0.1 다음 개발·검증 — 2026-10-31

## 결론

실DB 검증은 차단 상태다. 별도 권한으로 읽기 전용 TCP 연결을 재확인한 결과 `127.0.0.1:5432`, `[::1]:5432` 모두 `ECONNREFUSED`였다. 따라서 인증이나 SQL 실행 이전에 연결이 거부된다. 비밀번호 오류라고 추정하거나 자격증명을 변경하지 않았다.

기본 실행 경로에 `postgres`, `pg_ctl`, `psql`, `brew`, `docker`가 없고, `/Applications`에 Postgres.app/Docker가 없으며 `/opt`는 비어 있다. `/Library/PostgreSQL`, `/usr/local/pgsql`, `/opt/homebrew`, `/usr/local/Homebrew`, 사용자 Applications의 Postgres.app도 확인되지 않았다. 전체 디스크에 설치가 전혀 없다는 뜻은 아니다. 5432 LISTEN도 확인되지 않았다. 초기 제한 환경의 `EPERM`과 별도 권한 진단의 실제 `ECONNREFUSED`를 구분했다.

DB 설치·실행 경로와 관리자 접속 정보가 확인되지 않아 시스템 설치, 임의 비밀번호 시도, 기존 DB 초기화는 수행하지 않았다. 이번 작업에서 마이그레이션과 데이터 쓰기는 없다.

## 사용자에게 필요한 조치

1. 기존 PostgreSQL을 다른 위치에 설치했다면 **설치 경로와 시작 방법**을 알려준다. 비밀번호를 채팅에 붙여 넣을 필요는 없다. 기존 데이터 디렉터리를 삭제하거나 초기화하지 않는다.
2. 기존 설치가 없다면 [Postgres.app 공식 설치 안내](https://postgresapp.com/documentation/install.html)에 따라 앱을 다운로드해 Applications로 옮기고 실행한다. 프로젝트 요구 버전은 PostgreSQL 16 이상이다. **새 서버에만** Initialize를 누르고 실행 상태와 포트를 확인한다. macOS가 실행/접속 허용을 요청하면 해당 앱 및 개발 실행 도구에 대한 요청인지 확인한다. 이유: 현재 로컬 DB 서버가 연결을 받지 않기 때문이다.
3. 설치 후 알려주면 실행 도구를 절대 경로로 사용해 버전·포트·실제 접속 사용자·권한을 먼저 확인한다. 시스템 PATH 변경이나 sudo 설정은 필수가 아니다. 예: `/Applications/Postgres.app/Contents/Versions/latest/bin/psql`([공식 CLI 안내](https://postgresapp.com/documentation/cli-tools.html)). 접속 사용자나 비밀번호는 기존 설정을 확인하며 추측하지 않는다.
4. 접속 확인 후 **새 전용 폐기 가능 DB `node_test_alpha_01`**을 준비한다. 이름이 이미 사용 중이면 초기화하지 않고 새 이름을 택한다. 테스트는 관리자 연결로 스키마/임시 역할을 준비하고 HTTP 서버는 제한 역할로 실행하므로 DB 생성 및 역할 생성 권한 확인이 필요하다.
5. 검증된 로컬 연결 문자열을 실행 환경에만 주입하고 `NODE_TEST_DATABASE=1`로 `scripts/test.mjs`를 실행한다. 이 실행기는 대상 DB의 public 스키마를 초기화하므로 기존 개발 DB/사용자 데이터가 있는 DB에는 실행하지 않는다. 연결 문자열을 문서나 로그에 출력하지 않는다. 기존 001~008 마이그레이션, 업그레이드 보존 검사, 전체 실DB 회귀를 같은 실행기에서 수행한다.

실행 환경에는 번들 Node v24.22.1만 확인됐다. 프로젝트는 Node 22를 요구하므로 Node 22 설치/선택 후 동일 검사를 다시 실행해야 한다. Node 24 결과를 Node 22 검증으로 간주하지 않는다.

## 이번 변경

`tests/worker-alpha.integration.test.js`만 보강했다(기존 미추적 파일의 내용을 유지하며 확장). 애플리케이션, 첫 화면 문구·분기, 장비 카탈로그, 스키마, 매칭 기능은 변경하지 않았다.

추가된 실DB 검사 시나리오:

- 등록/재로그인 전후 회원 고유 ID 일치.
- 급여·지역을 실제 다른 값으로 수정하고 소유 장비를 별도로 추가한 뒤 버전 2 저장.
- 동일 계정에 업체 생성 후 company/worker 역할 공존 및 업체 ID 연결.
- HTTP 서버 종료·재시작 후 기존 서버 세션으로 `/api/me` 및 등록 정보 복원.
- 가짜 토큰 및 DB에서 만료시킨 세션 거부, 만료 토큰으로 수정 불가.
- 새 로그인 후 변경 문서 복원, 다른 회원 격리 및 기존 충돌/로그아웃 검사 유지.

**위 추가 시나리오는 문법 검사만 통과했으며 실DB 실행은 하지 못했다.** 이 테스트는 기존 전체 실행기에 이미 포함되어 있어 별도 등록은 필요 없다. 관리자 연결은 테스트 픽스처의 세션 만료에만 사용하고 HTTP는 기존 제한 역할을 사용한다.

UI 검사는 실제 DB 저장의 증거가 아니다. 알파 UI 스크린샷은 기존 파일 보존을 위해 `/private/tmp/alpha-next-worker-{390,1440}.png`에 저장했다. 기존 실행 중인 8047 서버를 중단하거나 교체하지 않았다.

기존 `03-2.test.cjs`는 숨겨진 `#specDetails > summary` 클릭에서 시간 초과로 실패했다. 현재 선택 입력은 상위 `#optionalDetails` 안에 있지만 이 검사 절차는 상위 영역을 먼저 열지 않는다. `03-2-a`도 같은 누락이 확인됐으며 전체 연속 실행을 중단했다. 기존 테스트를 통과했다고 재인용하지 않는다. 화면 변경 없이 검사 절차를 정비하고 전체 회귀를 재실행하는 작업이 남아 있다.

회귀 로그는 `docs/alpha-next-verification-logs/`에 보관했다. `03-2-a` 로그는 중단된 실행이며 완료 결과가 아니다. 이 실행에서 cargo/dump/flow/multisize는 미실행이다. 전체 UI 회귀 통과로 판단할 수 없다.

## 정책과 한계

- 이메일+비밀번호 인증, 별도 accounts.id, DB 세션의 해시/만료 검사는 기존 구현을 유지한다. 휴대전화·간편 로그인은 추가하지 않았다.
- 화면은 sessionStorage의 토큰으로 서버 `/api/me`를 확인한다. 같은 탭 새로고침/재접속 자동 복귀와 브라우저를 완전히 닫은 뒤 자동 로그인은 다르다. 후자는 현재 보장되지 않으며 지속 저장 방식으로 임의 변경하지 않았다.
- 역할은 account_roles와 organization_memberships가 같은 account_id를 참조하고 등록 API는 세션 ID를 사용한다. 이는 코드 확인 결과이며 실제 DB 정합성 검증을 대신하지 않는다.
- 매칭은 기존 준비 중 상태를 유지한다. 신규 기능, 푸시, 배포, 병합, 커밋은 수행하지 않았다. 기존 미커밋 파일과 데이터는 삭제·초기화하지 않았다.
