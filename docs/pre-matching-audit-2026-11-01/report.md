원본 DB 등록 문서는 장비작업자 **36개**, 기술작업자 **3개**, 업체 **16개**다. 운전능력 36건·보유장비 20건, 모집그룹 40개 중 기술그룹 8개다. 현재 validator 재검증은 장비작업자 36/36, 기술작업자 3/3, 업체 16/16 통과했다. 장비 부모·형태·규격·옵션에 업체의 엄격한 검증을 적용한 추가 검사는 운전능력 36/36·보유장비 20/20 통과했다.

**현재 원본에서 잘못된 장비 분류가 발견됐다는 뜻은 아니다. 잘못된 신규 요청을 막지 못하는 결함이 확인된 것이다.** 장비작업자 36개 문서 모두 catalogVersion이 없고, 업체 현장 16개 모두 구조화된 현장 지역코드가 없다. 필수조건 선택 수는 작업자 38개 문서가 0개·1개 문서가 1개, 업체 40개 그룹 모두 0개였다. 0개는 허용값이며 오류가 아니다.

기존 정규화 테이블의 occupations/regions/worksites/equipment/job_posts/job_lines/job_line_dates와 선호·구인조건 스냅샷, matches·추천기록은 원본에서 모두 0행이었다. 반면 등록 JSON 자료는 존재한다. 실제 API 실험에서도 등록 PUT 전후 관련 정규화 테이블 행 수가 바뀌지 않았다. 즉 현재 등록 완료가 기존 매칭 테이블 생성으로 이어지지 않는다. 원본은 합성 검증자료가 섞인 로컬 DB이므로 위 분포를 실제 서비스 사용자 통계로 해석하지 않는다.

[개인정보 없는 DB 집계](db-inventory.json), [원본 행 보존 로그](db-preservation.txt).

## 현재 구조를 재사용할 수 있는 부분

- 공통 직종/장비/지역 카탈로그와 ID, 기술직종 버전 검사, 5단계 선택기·옵션 UI. 새 분류표를 만들 필요는 없다.
- abilities/ownedEquipment 분리, account roles, 그룹 ID/headcount/occupationIds/all_per_person, 그룹별 requiredMatch.
- 원화 정수·단위, 지역코드·버전·legacyRegions, always/dates/range와 HH:mm, 우선순위 배열.
- 세션 기반 자기 정보 조회, 업체 소유권·권한 확인, JSON 문서 버전과 409 충돌·트랜잭션.
- 기존 sealed 선호·구인조건 버전, 약정·상호 승인·확정 이력, account/equipment 중복 예약과 날짜별 정원·취소 복구. 현재 004/007 스키마가 새 입력을 완전히 표현하는 것은 아니므로 **확장 또는 어댑터 없이 그대로 연결할 수 있다는 의미는 아니다.**
- 기존 지급/수령 사실 기록은 외부 정산 사실을 보존하는 데 사용한다. 추천 점수나 사용자 동의 없는 자동 정산으로 전환하지 않는다.

## 엔진 1차 개발을 위한 다음 작업 순서

1. **이번 보고서 검토·범위 승인.** 신규 엔진 구현과 선행 수정은 승인받기 전 시작하지 않는다. 1차 포함 작업자 유형·급여 단위·일정 범위·자격 확인 범위를 확정한다.
2. **공통 비교 계약 확정.** 양측 필수조건·unknown 처리·직종 AND·장비 공급·급여/경력/지역/일정·법정 관문의 사례 표와 오류 기준을 작성한다. 지원하지 않는 조합의 명시적 처리도 포함한다.
3. **좁은 데이터 무결성 수정.** 작업자 분류 검증, 업체 requiredMatch 생략 보존을 우선 수정하고 기존 문서·원문·직접입력·구형 요청을 회귀 검사한다. UI 변경이 필요한 부분은 별도 승인 범위로 둔다.
4. **원천 부족 보완 설계.** 기술작업자의 공통 희망조건·직종별 경력·업체 전용 필수항목 대응값과 계정별 법정 자격 구조를 확정한다. 승인 후 필요한 입력/API를 추가한다.
5. **연결·버전·중단 계약 설계 및 승인.** 기존 스냅샷·job_lines·그룹 인원·카탈로그 FK·예약 구간의 추가형 변경안을 만든다. 폐기 DB에서 무손실 이관·롤백·버전 충돌·삭제/비활성화·동시 정원 검증을 먼저 통과시킨다.
6. **별도 승인된 엔진 1차 구현.** 읽기 전용 스냅샷 입력으로 법정 관문 → 수행능력·양측 필수조건 → 중복/예약·남은 정원 → 조건별 사유 순으로 판정한다. 무작위 자료와 고정 사례로 양방향·AND·N명 distinct·unknown·단위차이·야간·동시 변경을 검증한다.
7. **제한된 추천 API·상호 수락 연결.** 자기 계정/자기 업체만 조회하고 기존 승인·확정 트랜잭션을 재사용한다. 수락 시 최신 버전·권한·자격·정원을 재검사한다. 추천 화면은 별도 승인 후 진행하며 계약·정산 기능을 확장하지 않는다.
