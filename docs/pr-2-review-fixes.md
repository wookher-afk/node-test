# PR #2 독립 검토 수정과 운영 전 조건

기존 001~004를 재작성하지 않고 `005_review_integrity_fixes.sql`로 수정합니다.
회원·프로필·업체·거래·지급·활동·평가·결정의 기존 행/ID/시각은 유지합니다.
새 DB는 001→005, 이미 004까지 적용한 검증 DB는 005만 추가합니다.
이번 작업은 개발 브랜치와 독립 테스트 DB에서만 수행하며 운영 적용/병합은 하지 않습니다.

## P1: 과거 거래의 업체 귀속과 접근 권한

`match_term_parties`는 조건 생성 시의 업체 ID를 불변으로 보관합니다.
현장→업체, 공고→현장, 모집 항목→공고 연결을 바꿔도 과거 거래의 업체가 바뀌지 않습니다.
거래 당사자 확인, 지급 의무 확인, 활동 집계, 재고용 비교, 조건 변경 계보는
현재 현장 소속 대신 이 스냅샷을 사용합니다.

사람의 실제 권한 철회는 계속 반영합니다. 과거 업체의 현행 owner/manager가 권한을 가지며,
업체를 떠난 직원의 권한을 영구 고정하거나 현장을 인수한 업체에 과거 거래 권한을 넘기지 않습니다.
신규 구인 관리/추천은 현재 업체 소속을 사용하고, 과거 거래에 관한 판단과 구분합니다.
원래 작성자의 정정/개인정보 신청 권한은 기존 정책을 유지합니다.

005 이전의 과거 업체 귀속은 현재 현장 구조만으로 복원할 수 없습니다.
**기존 조건 행이 있으면 검토 대응표 없이는 마이그레이션이 실패합니다.**
업체명/현재 소속에서 추측해 자동 이전하거나 원본을 바꾸지 않습니다.

## P2: 최신 정정 승인, 동시성, 재심 기각

- 새 결정은 `case_decision_order`의 서버 측 순서로 평가합니다. 사용자가 전달한
  `decided_at`이나 사건 번호로 미래 결정의 우선순위를 바꿀 수 없습니다.
- 활동/평가의 교체 버전은 그 기록에 대한 **현재 유효한 정정 승인 사건**을 명시해야 합니다.
  나중에 무효화된 승인, 더 최신 승인으로 대체된 승인, 미결 사건이 있는 상태의 승인은 사용할 수 없습니다.
- `dismissed`는 재심 요청의 기각이며 앞선 실체적 결정을 뒤집지 않습니다.
  무효→재심→기각은 무효로 남고, 무효→재심→유효 확인이면 유효 확인이 됩니다.
- 사건 접수, 결정, 교체 삽입은 동일 트랜잭션 잠금으로 직렬화합니다.
  정정이 먼저 커밋되면 그 당시의 승인으로 기록된 정정은 보존되고, 이후 원본 재심도 별도로 남습니다.
  무효 결정이 먼저 커밋되면 대기 중이던 교체는 최신 상태를 다시 읽고 거부됩니다.
  이미 교체된 버전 자체를 다투려면 해당 버전을 대상으로 별도 사건을 접수합니다.
- 이 쓰기 경로는 **READ COMMITTED**를 사용합니다. REPEATABLE READ/SERIALIZABLE 쓰기는
  잠금 이전 스냅샷 재사용을 피하기 위해 명시적으로 거부합니다. 읽기 전용 분석은 별개입니다.
- 005 이전에는 실제 결정 입력 순서가 독립적으로 보관되지 않았습니다.
  과거 결정이 있으면 검토된 순서표가 필요하며, 원본 시각을 근거 없이 다시 해석하지 않습니다.

## P2: 추천 시점에 실제로 존재했던 버전만 연결

추천의 선호/채용 조건은 해당 작업자·공고의 봉인된 버전이어야 하며,
생성 시각과 봉인 시각 모두 `shown_at`보다 늦으면 안 됩니다.
`feature_cutoff_at`이 있으면 그 더 이른 시점까지 존재/봉인된 버전만 허용합니다.
새 버전의 생성/봉인 시각은 DB가 기록하므로 과거 시각을 임의로 전달해 우회할 수 없습니다.

동일 트랜잭션에서도 `shown_at`은 실제 노출 시각을 써야 합니다. 트랜잭션 시작 시각인 `now()`를
새로 봉인한 버전 이후의 노출 시각으로 사용하면 시간 검사가 거부할 수 있습니다.

기존 추천에서 잘못 연결된 시간 순서가 발견되면 005를 전체 롤백하고 중단합니다.
원장을 자동 덮어쓰거나 삭제하지 않습니다. 별도 복제본에서 정정·제외 이력과
후속 학습 자료의 무효화 범위를 검토한 후 명시적인 개선 마이그레이션이 필요합니다.

## 기존 데이터의 검토 대응표 준비

아래는 **별도 복제본 리허설용 구조 예시**입니다. 테스트처럼 현재 구조를 SELECT해 채우는 것을
운영에서 사용하지 마세요. 실제 거래 자료와 감사 기록을 검토해 관리자가 명시적인 값을 넣어야 합니다.
표가 필요 없는 빈 DB는 준비 없이 005를 적용할 수 있습니다.

```sql
CREATE TABLE node_reviewed_match_parties (
  terms_id bigint PRIMARY KEY REFERENCES match_terms(id),
  organization_id bigint NOT NULL REFERENCES organizations(id),
  review_reference text NOT NULL CHECK(review_reference ~ '^[a-zA-Z0-9_.-]{1,128}$')
);
CREATE TABLE node_reviewed_case_decisions (
  case_id bigint PRIMARY KEY REFERENCES case_decisions(case_id),
  decision_order bigint NOT NULL UNIQUE CHECK(decision_order > 0),
  review_reference text NOT NULL CHECK(review_reference ~ '^[a-zA-Z0-9_.-]{1,128}$')
);
REVOKE ALL ON node_reviewed_match_parties,node_reviewed_case_decisions FROM PUBLIC;
```

각 조건/결정에 대한 정확한 업체·순서와 비식별 검토 문서 ID를 기입합니다.
005는 매핑 출처도 보존합니다. 증빙이 부족하면 이전을 진행하지 않습니다.
이전 후 대응표는 감사 정책에 맞춰 관리하며 공개 앱 권한을 부여하지 않습니다.
당사자 본인확인 자료/실명/연락처를 review_reference에 넣지 않습니다.

## 최소 권한: 이번 수정과 운영 적용 전 차단 항목

이번 수정에서는 NODE 함수(내부 조회 헬퍼 포함)의 PUBLIC 실행과 public 스키마의 PUBLIC CREATE를 회수합니다.
마이그레이션 실행 역할의 향후 함수 기본 EXECUTE도 PUBLIC에서 제거합니다.
새 귀속·결정 순서 테이블은 PUBLIC 접근 불가이며, SECURITY DEFINER로 우회하지 않습니다.
비소유자 역할에서 헬퍼 실행이 거부되는지 테스트합니다.

**이 조치만으로 운영 최소 권한이 완성되지는 않습니다. 다음은 운영 적용/신규 API 공개 전 필수입니다.**

1. 실제 Render 연결 역할의 소유권·superuser·BYPASSRLS·CREATE·광범위 GRANT·상속 역할을 확인합니다.
   이번 작업에서는 운영 DB에 접속하지 않았으므로 실제 운영 역할은 확인하지 않았습니다.
2. 마이그레이션 소유자와 런타임 역할을 분리합니다. 런타임에는 DDL/권한 관리/트리거 비활성화/
   원장·순서표·검토 대응표 임의 쓰기 권한을 주면 안 됩니다.
3. 현재 SQL은 invoker 권한을 사용합니다. 기존 역할에 직접 부여된 권한은 이번 PUBLIC 회수로 없어지지 않습니다.
   API별 필요한 테이블·시퀀스·헬퍼·트리거 경로를 나열해 허용 목록을 만들고 실제 비소유자 역할로 검증해야 합니다.
   함수 인자의 actor ID는 인증이 아니므로 무검증 SQL/RPC 노출은 금지합니다.
4. 과거 거래 SELECT는 고정된 업체 귀속과 세션 기반 권한으로 제한합니다.
   기존 뷰/테이블에는 전체 행 접근을 막는 완성된 RLS가 없습니다. 서버의 검증된 전용 API,
   필요한 경우 RLS/제한 뷰를 도입하고 업체 간 열람·조작 차단을 통합 테스트해야 합니다.
5. 관리자 심사와 일반 업무 역할을 분리하고, 개인정보 처리·학습 동의/철회·정정 전파·감사 로그의 권한을 확정합니다.
6. ALTER DEFAULT PRIVILEGES는 객체를 만드는 역할별 설정입니다. 이후 다른 배포 역할로 함수를 만들면
   그 역할에도 같은 기본 권한을 설정하고 기존 ACL을 재점검해야 합니다.

## 검증

기존 24개 회귀 테스트를 유지하고 소속 경로 3종 변경, 원래 업체의 승인/취소,
활동/평가의 승인 재사용 차단, 양방향 동시성 경합, 무효→재심→기각,
미래 버전/늦은 봉인/특징 기준 시점, PUBLIC 권한 거부를 추가 검증합니다.

기존 행·함수·권한과 새 구조가 전체 롤백되는지 확인합니다.
`npm test`는 명시적으로 허용한 로컬 일회용 DB에서만 실행합니다.
