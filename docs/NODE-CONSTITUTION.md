# NODE 개발 헌법

- 제정: 2026-10-27
- 지위: NODE 최상위 설계 원칙 (초판)
- 적용 범위: 기획·설계·개발·테스트·운영 및 GitHub 이슈·Codex 작업
- 표어: **모든 작업은 NODE로 통한다.**

NODE는 건설 현장의 작업자, 업체, 장비, 운송을 연결하고 작업 이력을 신뢰의 기반으로 만드는 플랫폼이다. 하위 정책과 구현은 본 헌법을 준수한다.

## 존재 목적

### 제1조 — 연결의 원칙

NODE는 작업을 필요로 하는 사람과 작업을 수행할 수 있는 사람 및 장비를 효율적으로 연결한다.

### 제2조 — 지속성의 원칙

NODE는 일회성 구인·구직을 넘어 작업자의 경력과 업체의 거래 이력이 지속적으로 축적되는 플랫폼을 지향한다.

### 제3조 — 신뢰의 원칙

NODE의 핵심 철학은 '일의 기록 = 신뢰'이다. 신뢰는 단순한 평점이 아니라 실제 작업과 거래의 기록을 바탕으로 형성되어야 한다.

## 사용자 권리

### 제4조 — 사용자 중심의 원칙

사용자는 복잡한 시스템을 이해할 의무가 없다. 내부 복잡성은 NODE가 처리하고 사용자는 필요한 정보 입력과 판단에 집중할 수 있어야 한다.

### 제5조 — 공정한 기회의 원칙

신규 가입자, 경력이 짧은 작업자, 거래 이력이 부족한 업체라는 이유만으로 부당하게 불이익을 주어서는 안 된다.

### 제6조 — 선택권의 원칙

작업자와 업체는 매칭을 수락하거나 거절할 자유가 있다. 정당한 선택, 거절, 미응답 자체를 신뢰도 하락의 근거로 삼지 않는다.

### 제7조 — 정보 자기결정권의 원칙

개인정보와 민감한 자료는 필요한 목적과 범위에서만 수집·사용한다. 정보 공개와 전달은 적절한 권한, 동의 및 접근 통제를 전제로 한다.

## 거래와 기록

### 제8조 — 상호 합의의 원칙

매칭은 작업자와 업체가 동일한 작업 조건을 승인해야 확정된다. 조건이 변경되면 필요한 당사자의 재승인을 받아야 한다.

### 제9조 — 사실과 평가의 분리의 원칙

객관적인 작업 사실, 당사자의 신고, 상대방의 확인, 주관적인 평가는 명확히 구분한다. 확인되지 않은 주장을 검증된 사실처럼 취급하지 않는다.

### 제10조 — 기록 보존과 정정의 원칙

작업·계약·지급 등 중요한 거래 기록의 변경 이력을 추적할 수 있어야 한다. 오류가 발견되면 정정과 이의제기가 가능해야 하며 법령에 따른 삭제·보존 의무도 준수한다.

### 제11조 — 상호 책임의 원칙

작업 완료와 대금 지급 등 중요한 거래 단계는 각 당사자의 책임과 확인 상태를 구분하여 기록한다. 한쪽의 일방적인 주장만으로 상대방의 의무 이행을 확정하지 않는다.

## 매칭과 기술

### 제12조 — 적합성의 원칙

매칭은 작업 분야, 자격, 숙련도, 일정, 지역, 장비, 보수 및 작업 조건을 종합적으로 고려한다. 신뢰, 개인의 선호, 작업 적합성은 서로 다른 판단 기준으로 관리한다.

### 제13조 — 자원 독립성의 원칙

작업자, 장비, 업체, 현장은 각각 독립적인 관리 대상이다. 하나의 계정이나 사용자가 복수의 역할·장비·현장·작업 분야를 보유할 수 있는 구조를 지원한다.

### 제14조 — 일정 정합성의 원칙

작업자와 장비의 확정된 작업 일정은 충돌하지 않아야 한다. 단, 일정이 비어 있다는 사실만으로 작업 가능 의사를 추정하지 않는다.

### 제15조 — 기술의 보조적 역할의 원칙

AI와 자동화는 사람의 판단을 지원해야 한다. 검증되지 않은 추정이나 편향된 데이터에 근거하여 사용자의 기회를 부당하게 제한해서는 안 된다.

## 개발과 변경

### 제16조 — 단계적 개발의 원칙

NODE는 핵심 기능부터 단계적으로 개발한다. 새로운 아이디어가 제시되었다는 이유만으로 기존 개발을 중단하거나 즉시 코드를 변경하지 않는다.

### 제17조 — 중요도와 긴급도의 분리의 원칙

개발 우선순위는 중요도와 긴급도를 구분하여 결정한다. 중요하지만 급하지 않은 사항은 기록하고 적절한 단계에서 반영하며 방치하여 긴급한 문제로 발전시키지 않는다.

### 제18조 — 기존 기능과 데이터 보호의 원칙

기능을 추가하거나 수정할 때 기존 데이터, 작업 이력, 사용자 권리 및 정상 작동하는 기능을 보호해야 한다. 변경에 따른 영향 분석과 검증을 수행한다.

### 제19조 — 설계 추적성의 원칙

확정된 요구사항은 GitHub에서 추적 가능해야 한다. 설계, 구현, 테스트, 배포 상태를 구분하고 중요한 결정과 변경 이유를 기록한다.

### 제20조 — 검증 우선의 원칙

코드 작성이 기능 완성을 의미하지 않는다. 기능은 정해진 요구사항에 따라 검증되어야 하며 보안과 데이터 정합성에 영향을 주는 변경은 관련 테스트를 거쳐야 한다.

## 헌법의 효력과 개정

### 제21조 — 최상위 규범의 원칙

NODE의 모든 세부 요구사항, GitHub 이슈, 설계 문서, Codex 개발 지시는 이 헌법을 준수해야 한다. 상충하는 경우 구현을 진행하기 전에 충돌을 해결한다.

### 제22조 — 헌법 개정의 원칙

이 헌법은 변경할 수 있다. 다만 개정에는 변경 이유, 기존 원칙과의 차이, 사용자와 시스템에 미치는 영향에 대한 검토 및 프로젝트 책임자의 명시적 승인이 필요하다.

## 충돌 검토 및 개정 절차

1. 신규 아이디어를 헌법·확정 요구사항·현재 구현과 대조한다.
2. 충돌이 없으면 GitHub에 요구사항과 우선순위를 기록하고 해당 개발 단계에서 구현한다.
3. 충돌이 있으면 기능을 임의로 구현하거나 헌법을 임의로 변경하지 않는다. 충돌 조항·대안·영향을 프로젝트 책임자에게 설명한다.
4. 꼭 필요한 기능을 위해 헌법 개정이 요구되는 경우 프로젝트 책임자와 상의하고 **명시적 승인** 후 개정한다. 개정 사유와 이전 버전은 Git 이력에 남긴다.
5. 보안·데이터 정합성·기존 기능 영향과 테스트를 점검한다. 개발 브랜치 기록은 운영 배포 승인이 아니다.
