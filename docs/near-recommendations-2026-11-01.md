# NODE 2단계: 근접 매칭 및 추천 우선순위

2026-11-01. 작업본 `/Users/heowook/Documents/ChatGPT/Node/node-alpha-01`, 브랜치 `feature/node-alpha-01-worker`.

## 구현

기존 `compareRegistration`과 `/api/companies/:id/auto-matches` 결과 계약은 유지했다. 추천만을 위한 `GET /api/companies/:id/recommendations`를 추가했다. 기존 라우터가 같은 인증·업체 멤버십 SQL 검사를 사용한다. POST는 405, 비회원 업체는 404, 비로그인은 401이다. 조회는 한 SQL 스냅샷의 문서·버전으로 계산하며 DB에 쓰지 않는다. 추천에서 제외된 사람은 API results에 포함하지 않는다. 순위는 모집항목별이며, 다른 모집항목 사이의 전역 순위는 아니다.

추천 자격은 기존 필수조건 합집합과 기본 게이트를 재사용한다. 장비 기종·형태·규격·요구 옵션, 해당 장비 경력, 모집 방식, 필수조건 선택 자료 및 추가 선택 필수조건은 유지한다. 규격 불일치·누락·직접 입력 동등성 미확인은 추천에서도 제외한다. 기술직은 기존의 한 사람당 모든 요구 직종 보유·경력 게이트를 유지한다. 자격증 등 법적 자격 검증은 기존 엔진 범위를 확장하지 않는다.

이번 추천에서만 pay와 schedule을 완화한다. 양측 유효 가격·동일 급여 단위 및 실제 작업일 자료가 있어야 하며, 단위 환산이나 미확정 일정 추측은 하지 않는다. 가격 차이 상한이나 최소 일정 충족률은 새로 만들지 않았다. 단 하루라도 실제 작업일과 겹치면 일정 추천 자격이 있다. 서로 겹치지 않으면 제외한다. 가격의 등록 유효 범위는 기존 검증 그대로다.

가격 결과는 `companyOfferWon`, `workerRequestedWon`, `differenceWon`(작업자-업체), `absoluteDifferenceWon`, `shortfallWon`(작업자 희망액이 업체 제시액을 초과한 금액), `payUnit`을 표시한다. 제시가격 차이를 거래가격으로 확정하지 않는다. 기존 급여 충족 의미인 업체 제시액 ≥ 작업자 희망액은 그대로다. 따라서 가격이 달라도 업체 제시액이 높으면 급여 조건은 충족한다.

일정은 UTC의 날짜 단위로 양끝을 포함해 계산한다. 날짜 목록, 기간, 작업자 항상 가능 및 기존 availableDates를 처리한다. 업체 항상 가능은 실제 작업일을 알 수 없으므로 제외한다. `requestedPeriods`, `coveredPeriods`, `uncoveredPeriods`는 각각 실제 요청·충족·미충족 날짜의 연속 구간 목록이며, 구간 안 모든 날짜를 뜻한다. `requestedDays`, `coveredDays`, `uncoveredDays`, `coverageRatio`도 반환한다. 달력 일수를 무제한 펼치지 않고 구간 교차로 계산한다. 날짜 목록의 빈 날은 요청일로 추가하지 않는다.

추천 결과에는 원래 정확 매칭 결과를 `exactMatch`로 함께 둔다. `tier=full`은 기존 정확 매칭 통과 및 계산된 모든 비교조건 pass, `tier=near`는 추천 자격이 있으나 비교조건에 차이 또는 미확인이 있는 경우다. 기존 선택하지 않은 희망조건은 계속 필수 게이트가 아니다. 따라서 선택하지 않은 근무시간이 다르면 기존 `exactMatch.matched=true`이면서 추천 `tier=near`일 수 있다. `differences`가 그 이유를 제공한다. `tier`로 기존 정확 매칭 판정을 대체해서는 안 된다.

## 교체 가능한 임시 정렬: temporary-pareto-v1

정렬 정책은 `server/recommendation-ranking.js`에 분리했다. 응답에 `policy`와 `temporaryPolicy=true`를 명시한다.

1. full을 near보다 먼저 둔다.
2. 같은 tier·모집항목 안에서, 일정 충족일수가 더 적지 않고 절대 가격 차이도 더 크지 않으며 둘 중 하나가 엄격히 나은 후보가 다른 후보를 지배한다. 같은 모집항목은 요청일 분모가 동일하므로 충족일수 비교는 충족률 비교와 같다.
3. 아무에게도 지배되지 않는 후보를 첫 묶음으로 꺼내고, 남은 후보에 같은 계산을 반복한다. `priorityGroup`은 `full:0`, `near:0`, `near:1` 등이다.
4. 같은 묶음의 동점 및 서로 상충하는 후보는 작업자 계정 ID 오름차순으로 순서만 고정한다. 정수 ID는 문자열 길이·문자열 순서로 비교해 큰 bigint 정밀도 손실과 입력 순서 의존을 피한다. `position`은 모집항목별 1부터 시작한다.

가격과 일정이 상충하는 후보 사이의 가중치나 절대 우선순위를 확정하지 않는다. 같은 priorityGroup 안의 낮은 position은 업무상 우월함을 뜻하지 않는다. ID는 선착순 수락이나 거래 우선권을 뜻하지 않는다. 절대 가격 차이를 사용하는 것 자체도 이번 임시 규칙이며 영구 정책이 아니다.

## 실제 API 예시

업체 미니 017, 일급 550,000원, 2026-11-02~30(29일), 나머지 기본·필수조건 충족:

| 후보 | 희망 일급 | 실제 충족 구간 | 충족/미충족 | 가격차(작업자-업체) | 추천 |
|---|---:|---|---|---:|---|
| A | 550,000 | 11/02~30 | 29/0일 | 0 | full:0, 첫 번째 |
| B | 570,000 | 11/02~30 | 29/0일 | +20,000 | near:0 |
| C | 550,000 | 11/02~17 | 16/13일 | 0 | near:0 |
| D(020) | 550,000 | 전체 | — | 0 | 제외 |
| 빈 규격 | 550,000 | 전체 | — | 0 | 제외 |
| 12/01~02만 가능 | 550,000 | 없음 | 0/29일 | 0 | 제외 |

B와 C는 같은 우선순위 묶음이다. C 미충족 구간은 11/18~30이고 충족률은 16/29이다. 실제 통합 테스트에서는 B 계정 ID가 C보다 작아서 B를 먼저 표시했다. 이 순서는 가격보다 일정이 항상 중요하다는 정책을 뜻하지 않는다. 원문 응답은 검증 로그 `integration.txt`에 있다.
