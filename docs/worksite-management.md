# 현장 관리 API 구현과 검증 기준

이번 3차 작업지시서 4~8항을 구현 기준으로 사용한다. 별도 ‘현장 설계 18개 항목’ 문서는 저장소에 없으며, 사용자가 이번 지시서에 해당 설계가 포함됐다고 확인했다. 운영정책 230건을 수정하거나 전체 0.1 범위를 확정한 문서가 아니다.

근거: 헌법 제7·10·13·18~20조, DB-004~006, P-30·33·36, C12, F07, D01·D02. 현장 기본정보 관리와 거래 상세 열람은 별개다. 근무 확인 권한을 저장해도 근무 확인·계약·지급 API가 추가되는 것은 아니다.

## 접근 기준

| 대상 | 조회 | 등록·담당자 권한 부여/회수 | 수정 | 비활성화 |
| --- | --- | --- | --- | --- |
| 현재 업체 owner/manager | 해당 업체의 현장 기본정보 | 허용 | 허용 | 허용 |
| 현재 staff | 현재 view 권한을 부여받은 현장만 | 불가 | 해당 현장의 edit가 참인 경우만 | 해당 현장의 deactivate가 참인 경우만 |
| 타 업체·무소속 | 존재를 숨기는 404 | 404 | 404 | 404 |

담당자 지정 자체가 업체 관리자 역할을 부여하지 않는다. `view`, `edit`, `deactivate`, `confirm_work`는 각각 독립 불리언이며 지정 시 네 값을 모두 입력한다. 담당자에게는 view가 필요하고 나머지는 명시적으로 부여한다. `confirm_work`로 수정·비활성화·담당자 지정 권한이 생기지 않는다. 소속 종료는 담당자 active를 거짓으로 바꾸고 이력을 남기며, 재소속만으로 권한을 복원하지 않는다.

모든 현장 요청은 공통 세션 인증을 사용한다. 현장 DB 트랜잭션에서 기존 advisory lock `(710031,1)`을 획득한 뒤 세션·현재 소속·현장 권한을 다시 확인한다. 읽기도 같은 순서를 사용하여 권한 회수와 일관된 처리 순서를 갖는다. 외부 요청에서 행위자·역할을 받아 신뢰하지 않는다. 현장 이관은 API에서 허용하지 않는다. 기존 DB의 소속 변경 경로가 사용되더라도 담당자 권한은 회수되고 005의 과거 거래 업체 스냅샷은 유지된다.

본문 수신·JSON 파싱·필드/자료형/길이/버전 형식 검증은 현장 DB 연결과 공통 잠금 획득 전에 완료한다. DB에 참조 지역·현재 소속이 존재하는지, 현재 업무 권한과 대상 version이 유효한지는 잠금 뒤에 검사한다. 공통 인증은 `clock_timestamp()`의 실제 검사 시각으로 세션 만료를 판단하므로 잠금 대기 중 만료된 요청도 401로 거부한다. 트랜잭션 시작 시각인 `now()`를 인증 만료 판정에 사용하지 않는다.

## API와 입력

기존과 같이 Bearer 세션 토큰을 사용한다. bigint 식별자는 JSON 정밀도 손실을 피하려고 양의 정수 **문자열**로 취급한다. 성공 응답은 `{worksite: {...}}`, 목록은 `{worksites: [...]}`다. 담당자 관리 응답에는 권한과 계정 식별자만 포함하며 연락처·비밀번호·근무·계약·지급 상세는 반환하지 않는다.

| 메서드·경로 | 입력·응답 |
| --- | --- |
| POST `/api/companies/:companyId/worksites` | 필수 name·address, 선택 region_id·location_notes·description. 201, worksite와 warnings |
| GET `/api/companies/:companyId/worksites` | 권한 범위 안의 활성/비활성 현장 목록, 200 |
| GET `/api/worksites/:siteId` | 허용된 현장 기본정보, 200 |
| PATCH `/api/worksites/:siteId` | 필수 version과 수정할 기본정보만, 200 |
| POST `/api/worksites/:siteId/deactivate` | `{version: 1}`, 비활성화 후 기본정보, 200 |
| GET `/api/worksites/:siteId/assignments` | owner/manager만. 현재 version과 담당자별 저장 권한·유효 여부 |
| PUT `/api/worksites/:siteId/assignments/:accountId` | `{version: 1, permissions: {view: true, edit: false, deactivate: false, confirm_work: false}}` |
| DELETE `/api/worksites/:siteId/assignments/:accountId` | `{version: 1}`. 행 삭제 없이 담당자 active만 거짓으로 변경 |

수정·비활성화·담당자 변경 시 직전 조회의 정수 version을 제출한다. 한 요청이 성공하면 현장 version이 증가하고 같은 이전 version의 다른 요청은 409다. 담당자 변경과 현장 정보 변경도 하나의 버전으로 충돌을 확인한다. 소속 종료는 별도 권한 회수 사건이며 버전이 같더라도 권한 검사를 통과할 수 없다.

name은 1~120자, address는 1~500자이며 앞뒤 공백 제거 후 비어 있으면 거부한다. 선택 location_notes는 1000자, description은 3000자 이하 문자열 또는 null이며 빈 문자열은 null로 저장한다. 이는 저장·요청 검증 한계이며 새 사업정책이 아니다. region_id는 기존 지역 ID 또는 null이다. 미등록 지역·잘못된 자료형·알 수 없는 필드·소속 업체나 등록자 위조 필드는 400이다. 역할상 금지는 403, 없는 대상/타 업체/현장 조회 권한 없음은 동일한 404, 인증 실패는 401, 버전 충돌/이미 비활성화는 409다.

중복 검사에서는 같은 업체의 이름 또는 주소에서 공백·문장부호·대소문자를 정규화하여 비교한다. 유사하면 `warnings: [{code: "similar_worksite", message: "...", count: 1}]`를 반환하되 등록은 성공한다. 실제 동일 현장 판정·주소 검증·지도·지오코딩·도로거리 기능은 아니다. 다른 업체 데이터는 경고에 사용하지 않는다.

## 신규 마이그레이션 006

`database/006_worksite_management.sql`을 005 이후 **한 번** 적용하는 추가 마이그레이션이다. 기존 001~005를 수정하지 않는다. 적용 시 잠금이 있으므로 운영 무중단 적용을 보장하지 않는다.

- worksites: address·location_notes·description·created_by/at·updated_by/at 추가. 기존 행은 알 수 없는 값을 NULL로 유지한다. is_active 기본 true, version 기본 1. 신규 API 등록에서는 주소와 등록자·시각을 채운다.
- 기존 현장은 주소가 없어도 이전·조회 가능하며, 입력한 항목만 명시적으로 보완한다. 등록 당시의 알 수 없는 시각을 수정 시각으로 소급하지 않는다.
- worksite_assignments: 현장·업체·계정 연결과 네 개의 개별 권한, 활성 여부·부여/변경자를 관리한다. 같은 현장에 복수 담당자 가능. 현재 소속 검사와 소속 종료/이관 자동 회수 트리거가 있다.
- worksite_events: 생성·수정·비활성화·권한 부여/변경/회수·소속 종료/이관의 전후 내용·행위자·시각을 추가 기록한다. 기존 거래나 과거 현장 이력을 추정 생성하지 않는다. API 밖의 기존 DB 변경은 행위자를 알 수 없으면 NULL로 남긴다.
- 이력 변경·현장 물리 삭제를 트리거로 막고, 일반 런타임에 이력 직접 쓰기 권한을 주지 않는다. 좁은 SECURITY DEFINER 트리거만 이력을 기록하며 search_path를 고정하고 PUBLIC 실행 권한을 회수한다.
- 기존 job_posts.worksite_id, 현장 ID, 조직·회원·매칭·지급·예약·기록 값은 유지한다. 비활성화는 과거 기록을 지우거나 기존 계약을 변경하지 않는다.

## 개발·검증과 운영 경계

`npm test`는 기존처럼 명시적으로 승인한 로컬 폐기용 node_test DB만 초기화한다. 신규 설치 001~006, 기존 회원/거래가 있는 005→006의 전후 값 비교, 006 마지막 단계 실패의 전체 롤백과 원래 71개 테스트를 유지하며 현장 HTTP·동시성·권한 테스트를 추가한다.

기존 회원용 제한 DB 역할은 그대로 유지한다. `scripts/lib/test-worksite-role.mjs`는 로컬에 별도 임시 현장 역할을 만든다. 비밀번호 해시·회원/업체 생성·공고·매칭·지급·원장 직접 쓰기·DDL 권한은 없다. 서버의 WORKSITE_DATABASE_URL은 회원 DB와 같은 호스트·포트·DB·접속 옵션이어야 하며 계정만 분리할 수 있다. 미설정 시 기존 DATABASE_URL을 사용하지만 기존 회원 역할에는 현장 권한이 없어 현장 업무를 실행할 수 없다. `npm run dev:local`은 준비된 로컬 DB에 두 임시 역할을 구성하고 종료 시 회수한다.

업체/현장별 사용자 접근은 서버에서 집행한다. 별도 현장 역할도 신뢰된 서버용이며 사용자별 RLS 격리 완료를 뜻하지 않는다. 사용자에게 직접 DB 접속을 허용하지 않는다. 운영 역할 설정·비밀 설정·실제 DB 이전은 승인된 복제본 리허설과 별도 운영 적용 승인이 필요하다. 서버 시작·Docker 시작은 마이그레이션을 실행하지 않는다.

이번 구현은 API와 DB 기반이다. 기존 회원 화면은 변경하지 않는다. 직원 초대, 현장 이관/재활성화, 공고·매칭·근무 확인·계약·지급 업무, 지도는 추가하지 않는다. 비활성 현장에 새 공고를 허용할지는 이번 구현으로 결정하지 않으며 향후 공고 단계에서 확인해야 한다. 변경 이력의 법적 보존기간·삭제/익명화 절차는 C09의 별도 검토 대상으로, 이번에 임의 기간이나 무기한 보존 정책을 정하지 않는다.
