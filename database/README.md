# NODE database — single source of truth

PostgreSQL 16+, Node.js 22. `database/`가 회원과 매칭의 유일한 스키마입니다.
`001_foundation.sql`과 `002_accounts.sql`은 기존 배포본 그대로 보존합니다.
`003_unified_matching.sql`, `004_work_records_and_matching_data.sql`, `005_review_integrity_fixes.sql`, `006_worksite_management.sql`은 이를 확장하는 **한 번만 실행하는** 트랜잭션 마이그레이션입니다.
서버 시작, Docker 시작, CI는 운영 DB를 마이그레이션하지 않습니다.

## 개발 환경

1. `nvm use` (22), `npm ci`.
2. 별도 로컬 PostgreSQL 16에 빈 `node_test` DB를 준비합니다. `.env.example` 참고.
3. 테스트: `NODE_TEST_DATABASE=1 DATABASE_URL=postgresql://node:node_test_only@127.0.0.1:5432/node_test npm test`.
   **이 명령은 해당 테스트 DB의 public 스키마를 초기화합니다.** 실행기는 명시적 확인 변수,
   로컬 호스트 허용 목록, `node_test` 이름을 모두 검사합니다. 운영 주소는 허용하지 않습니다.
4. 테스트는 기존 001 스모크 → 002 → 가상 기존 회원 데이터 → 003/004 업그레이드 →
   회원 HTTP 회귀 및 같은 DB의 매칭/동시성 통합 테스트 순서로 실행합니다.
5. 개발 서버는 테스트 후 해당 DB를 사용해 `DATABASE_URL=... npm start`.
   `.env` 파일은 자동 로딩되지 않습니다. 운영 연결 문자열을 개발 파일에 복사하지 마세요.

새로운 별도 개발 DB를 수동 구성할 때만 001 → 002 → 003 → 004 → 005 → 006을 `psql -v ON_ERROR_STOP=1 -f ...`로 적용합니다.
기존 DB에는 001을 다시 실행하지 않습니다. `db/`의 과거 UUID SQL은 사용하지 않습니다.

## 보존 범위와 사전 검사

003은 기존 계정, 비밀번호 해시, 역할, 작업자 경력, 업체, 소속, 세션을 재작성하거나 ID를 변경하지 않습니다.
회원 테이블을 DROP/TRUNCATE하지 않습니다. 추가되는 것은 매칭 이력 테이블/인덱스,
취소 메타데이터, 보호 트리거와 함수입니다.

UUID 실험 테이블 `users`/`companies` 또는 기존 `matches`/`match_approvals` 데이터가 있으면
마이그레이션 전체가 실패하고 롤백됩니다. 이는 기존 매칭 이력을 추측해 재해석하지 않기 위한 사전 검사입니다.
그 경우 데이터를 지우지 말고 별도 복제본에서 개별 이전안을 작성해야 합니다.
적용 후 `match_events` 존재와 취소 컬럼, 함수 시그니처를 확인하고 적용 커밋/파일 체크섬을 기록합니다.
이 단계에서는 범용 자동 마이그레이션 실행기를 추가하지 않았으며 003 재실행은 지원하지 않습니다.

## 매칭 보장

- 기존 bigint `accounts` / `organizations` / `job_lines`를 그대로 사용.
- `node_approve_match(match_id, terms_id, party, actor_id)`: 작업자 본인 또는 업체 owner/manager만 승인.
- `node_confirm_match(match_id)`: 같은 최신 조건 양측 승인, 모집 중, 부분 지원 정책,
  날짜별 정원, 외부/휴가 일정, 작업자 및 장비 예약 충돌 검사 후 원자적 확정.
- `node_cancel_match(match_id, actor_id, reason)`: 당사자 확인, 사유/주체/이력 보존,
  같은 트랜잭션에서 예약 해제 및 정원 복구.
- 승인된 조건/날짜는 불변. 변경 시 새 버전과 새 pending 매칭에 재승인.
- 직접 confirmed INSERT, 확정 매칭 조건 교체, 정원 축소 및 예약 직접 삭제를 차단.
- 완료 매칭도 해당 날짜 정원과 예약을 유지.
- 한국 시간 하루 단위 예약. 시간제/반일 일정은 후속 설계 대상.

초기 버전은 관련 쓰기를 하나의 트랜잭션 advisory lock으로 직렬화합니다.
동시 확정·정원 변경·일정 변경이 같은 규약을 사용하도록 BEFORE STATEMENT 트리거를 둡니다.
규모가 커지면 날짜/자원별 잠금으로 개선해야 하며, 지금은 처리량보다 정합성을 우선합니다.

## 권한 경계 및 남은 범위

SQL의 actor ID는 인증 수단이 아닙니다. 향후 서버 API는 세션에서 actor를 가져오고
세부 액션 권한을 검사해야 합니다. 공개 매칭 API는 이번 변경에 포함하지 않습니다.
매칭 함수의 PUBLIC 실행 권한은 철회합니다. DB 소유자는 신뢰된 관리자이며
테이블/트리거를 우회할 수 있으므로 일반 사용자의 직접 DB 접속을 허용하면 안 됩니다.
운영 서비스용 최소 권한 역할·GRANT·비밀 관리 정책은 실제 배포 전에 별도 검토합니다.

장비+기사는 공급 작업자가 소유/관리하는 장비만 지원합니다. 장비만 매칭은 명시적으로 거부합니다.
근무 가능 요일/명시적 가용일 산출, 장비 기사 위임, 운송, 모집 마감 시각,
전자계약·양측 완료 확인·지급·알림은 완료되지 않았습니다.
일정 충돌이 없다는 것은 근무 가능 의사 확인을 대체하지 않습니다.

## 향후 운영 적용 순서 — 이번 작업에서는 실행하지 않음

1. Render가 사용하는 브랜치/커밋, Neon의 실제 스키마와 적용 이력을 읽기 전용으로 확인.
2. 백업/PITR 복구 지점 확보, 별도 Neon 브랜치/복제본에서 기존 데이터로 003 적용 리허설.
3. 계정/프로필/업체/소속/세션의 행 수·내용·ID·시퀀스와 기존 로그인 회귀 확인.
4. 기존 매칭 데이터/예약이 있으면 자동 적용을 중단하고 별도 이전 계획 수립.
5. 유지보수 시간 및 롤백 계획 승인 후, 신뢰된 관리자가 미적용 버전(003 → 004 → 005 → 006)만 순서대로 한 번 적용. 005 이전에는 검토 대응표와 기존 추천 시간 순서를 검증. 006은 아래 현장 관리 문서의 NULL 전환·접근 역할·권한 회수·보존 검증을 별도 복제본에서 확인.
6. 적용 버전 기록, 회원 기능 확인 후 후속 매칭 API 배포를 별도로 진행.

003은 테이블 잠금과 트리거 교체가 있으므로 무중단을 보장하지 않습니다.
COMMIT 전 오류는 전체 롤백됩니다. COMMIT 후에는 새 이력이 생길 수 있으므로 역방향 DROP SQL을
자동 실행하지 말고 백업 복구 또는 전진 수정안을 검토합니다. 기존 서버는 회원 테이블이 같아
새 스키마와 호환되지만, 앱 되돌리기와 DB 되돌리기는 다른 절차입니다.

## Docker 검증

일반 환경: `docker build -t node-app:test .`.
회사/개발 환경의 HTTPS 프록시 인증서가 필요한 경우에만
`docker build --secret id=proxy_ca,src=/path/to/ca-bundle.pem -t node-app:test .`.
인증서는 BuildKit 임시 마운트로만 전달하며 이미지에는 복사하지 않습니다.
TLS 검증을 끄지 않습니다. 운영 이미지의 설치도 `npm ci --omit=dev`를 사용합니다.

## 일의 기록·신뢰·선호·작업 적합도

004는 회원/매칭 원본을 변경하지 않고 활동·평가·선호·추천 이력 기반을 추가합니다.
점수/AI 모델은 구현하지 않습니다. 기록 상태·이의제기·정정·학습 동의·개인정보 정책과
수집 API가 아직 없는 범위는 [설계 원칙](../docs/work-records-and-trust.md)을 참조하세요.

## 독립 검토 수정 (005)

과거 거래 업체 귀속 고정, 최신 유효 정정 결정/재심 기각 처리, 동시성, 추천 시점 검증과
PUBLIC 권한 회수는 [수정·운영 전 조건](../docs/pr-2-review-fixes.md)을 따릅니다.
기존 조건/결정이 있는 DB에는 검토된 업체 대응표/결정 순서표 없이 005를 적용하지 않습니다.
런타임 역할 분리·행 접근 통제는 여전히 운영 전 필수이며 실제 운영 권한은 확인하지 않았습니다.

## 1차 안정화: 로컬 회원 서버 최소 권한

`npm test`는 관리자 연결로만 스키마/픽스처를 준비하고, 회원 HTTP 서버는 별도 최소 권한 역할로 실행합니다.
준비된 로컬 테스트 DB는 `npm run dev:local`로 같은 제한 역할을 이용할 수 있습니다.
원격/운영 연결은 거부하며 운영에 자동 적용하지 않습니다.
[권한 목록·실행 절차·제약](../docs/stabilization-1.md)을 먼저 확인하세요.

## 현장 관리 (006)

현장 주소·상태·등록/변경자·버전, 담당자별 개별 권한, 변경/권한 회수 이력을 추가합니다.
기존 현장의 미상 주소·등록자·시각은 NULL로 유지하고 기존 현장 ID·공고·거래 외래키를 보존합니다.
로컬 개발에서는 기존 회원 역할과 별도 임시 현장 역할을 사용합니다. 운영 역할을 자동 설치하지 않습니다.
[API·권한·마이그레이션·운영 전 조건](../docs/worksite-management.md)을 확인하세요.
